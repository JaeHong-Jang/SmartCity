# ADR 0010: Phase 4 — 다양성, AI 도로, 시뮬레이터 모드(사고·통제·수요 급증·정전·화재 대응)

- 상태: Accepted · 날짜: 2026-10-25 · 결정자: Opus (council: Astra, Sol — Argon은 사용량 한도로 불참, Sol이 대체)
- 제안서: `harness/runs/4c/proposal.md` · council 원문: `harness/runs/20261025-145036-phase4bc/{astra,sol}.md`
- 조사: [10 시티빌더 레퍼런스](../research/10-citysim-references.md), [11 스튜디오 UX·AI 이미지](../research/11-studio-ux-and-ai-image.md)
- 두 리뷰 모두 "조건부 동의". 둘 다 로컬 파일을 읽지 못해 제안서 기반 설계 검토였다. 코드 사실은 구현 단계에서 확인한다.

## 맥락
사용자 요구:
- "시뮬레이터"를 누르면 지금 도시로 순환과 문제 대응을 보여 준다. 다른 사람에게 영향이 없어야 한다.
- 사건은 4종 모두 다룬다: 사고·통제, 화재·응급, 정전, 수요 급증.
- 건물·차량의 다양성을 높인다. 절차 생성과 CC0 에셋을 쓰고, Blender는 오프라인 도구로만 쓴다.
- AI가 도로를 짓는다.

## 범위 결정 (council 권고 반영)
- **4b의 차량 다양성은 외형만** 다룬다. 동역학(길이·가속)은 기존 그대로 두고, 골든 해시도 그대로다. 클래스별 동역학은 후속 과제다.
- **ON/OFF 비교는 순차 실행이 기본**이다. 병렬 워커는 기기 측정 뒤 선택 기능으로 넣는다.
- **우회(재탐색)는 폐쇄·장애물 회피와 자유류 비용만** 쓴다. 혼잡 통행시간 평활은 후속이다.
- **후속으로 뺀 것**:
  - 인접 변전소 재분배
  - 버스 자동 증차
  - 견인차
  - 일반 차량의 긴급차 양보
  - 적응 신호(Max-Pressure)
- 4c2는 두 묶음으로 나누고 각각 따로 리뷰한다. ① 시설 + 출동 + 신호 선점, ② 정전 + 배터리.

## 결정

### 1. 시뮬레이터 모드 격리 (D1)
- **사본 생성:** 진입 시 마지막으로 적용된 서버 `seq`(baseSeq) 경계에서 `CityDoc`을 복제해 **별도 워커**를 만든다.
  - 서버에 보내는 것은 없다. 공유 명령 경로와 분리되어 있으므로 실험 때문에 서버 sim 부하가 늘지 않는다.
- **시작 상태:** "현재 교통 상태"가 아니라 **"현재 도시 설계로 새 실험"**이다. 정해진 준비 운행(warm-up, 기본 게임 10분)을 고속으로 돌린 뒤 사건을 주입할 수 있다.
  - UI에도 이렇게 명시한다. 진행 중인 교통을 그대로 이어받으려면 완전한 sim 체크포인트가 필요한데, 이는 후속 과제다.
- **메인 워커:** 진입 동안 일시정지한다(기존 일시정지와 같은 의미). 공유 명령은 계속 수신·적용하고, 나가면 재개한다.
  - 사본은 고정이다. 상단에 "기준: seq N, 시각" 배지를 띄우고, 최신 도시로 다시 시작하는 버튼을 둔다.
- **종료 시 정리:** 실험 워커·구독·스냅샷 버퍼를 해제한다. 반복 진입·이탈 시 누수가 없는지 테스트한다.

### 2. 사건 입력 계약 (D2) — Command 경계
- **경계를 명시한다:**
  - 영속 도시 편집은 `Command → applyCommand()`이며 변경 없다.
  - **실험 입력**은 `ScenarioInput`으로, sim 안의 단일 경로 `applyScenarioInput(world, input)`에서만 sim 실행 상태를 바꾼다. 이 경로는 검증되고 기록된다.
  - 렌더러는 스냅샷만 읽는다. UI가 world를 직접 수정하지 않는다.
- **`ScenarioInput` 형식:** `{ eventId, tick, order, kind, target(안정 ID), params }`.
  - 워커는 **확정된 tick 경계**에서만 적용한다. 정렬 키는 `(tick, order, eventId)`다.
  - 이미 지난 tick을 대상으로 한 입력은 거부한다.
- **시나리오 기록:** `{ engineVersion, scenarioVersion, baseSeq, doc(복제본 전체), seed, tickRate, warmupTicks, inputs[], policy }`.
  - 같은 기록이면 같은 tick 상태가 나와야 한다(재생 테스트).
- **효과 합성:** 사건별 효과 레코드를 보존하고, 매 tick 합성한다.
  - 차단 = OR, 속도 계수 = 최솟값.
  - 위치 장애물은 별도 목록으로 둔다.
  - 한 사건이 끝나도 다른 사건의 효과는 유지된다.
- **재컴파일 금지:** 오버라이드는 차선·커넥터·교차로 단위 배열로 둔다.
  - 사건이 없을 때 기존 경로는 RNG 소비·연산 순서·스냅샷이 모두 같아야 한다. **골든 해시 불변 테스트**로 증명한다.

- **입력 검증 경계(구현 중 확정)**:
  - 큐잉 시에는 **정적 검증만** 한다. 대상은 형식, 허용 키 화이트리스트, 유한한 숫자, 지난 tick, 중복 eventId, 참조 대상의 존재다.
  - 사건 활성 여부, 이미 종료됐는지, 종료가 예약됐는지는 **적용 시점**에 판단한다. 해당하면 결정적 no-op으로 처리하고 로그에 남긴다. 그래서 실시간 실행과 재생이 구조적으로 같다.
  - 적용 결과는 무손실 스트림(`drainScenarioOutcomes` / 워커 `outcomes`)으로 UI에 전달한다.
  - 시나리오 기록은 아직 저장·내보내기를 하지 않는다(세션 메모리에만 있다). 그래서 기록 형식은 엄격하게 둔다. 저장 기능을 도입할 때 `scenarioVersion`과 정규화를 추가한다.

### 3. 사건 최소 모델 (D3)
물리 효과는 ON과 OFF가 같고, **대응 정책만** 다르다. OFF에서도 기본 안전 규칙은 유지한다.

| 사건 | 효과 (ON/OFF 공통) | 대응 ON |
|---|---|---|
| 도로 통제 | 차선 입구와 그 차선으로 들어가는 커넥터 모두 신규 진입 금지. 내부 차량은 배출 | 영향 차량 재탐색 |
| 사고 | 한 차선 위치에 **가상 정지 장애물**(통행 KPI에 섞이지 않는 비차량). 이미 차량이 있는 지점에는 겹치지 않게 그 앞의 빈 위치에 둔다. 고정 지속 시간 | 영향 차량 재탐색 |
| 수요 급증 | **사전 생성한 추가 통행 목록**(유입 시간표 + 종료 후 유출 시간표). 기존 수단 선택 규칙을 따른다 | 재탐색만(버스 증차는 후속) |
| 정전 (4c2-②) | 담당 구역 신호 소등 → 안전한 비신호 운영. 녹색에서 바뀔 때 교차로 안 차량은 배출. 건물 창 소등 | 스마트 신호 배터리 유지(N분) |
| 화재·응급 (4c2-①) | 사건 진행도(0→100). 시설에서 출동해 도착 후 처리. 시설이 없거나 경로가 단절되면 **"출동 불가"** | 긴급차 신호 선점 |

- **비신호 게이트:** 기존 게이트가 전방향 일시정지·공정성·교착 회피를 보장하는지 4c2-② 전에 테스트로 확인한다. 부족하면 보완한다.

### 4. 신호 상태 머신 (council 블로커)
- 교차로마다 **하나의 제어 상태 머신**을 둔다.
  - 우선순위: 정전/배터리 상태(제어 가능 여부) > 선점 요청 > 기본 플랜.
- 모든 전환은 최소 녹색, 황색, 전적색, 보행자 정리 시간을 지킨다. 스크램블 위상과도 같은 규칙이다.
- 복수 선점 요청은 도착 예상 tick이 빠른 순으로, 동률이면 차량 ID 순으로 처리한다.
- 적응 신호는 나중에 이 머신의 "요청자"로 추가한다.
- **4c2-① 구현 확정**
  - **모드:** NORMAL, PREEMPT, DARK가 있다. DARK는 4c2-②에서 쓰려고 자리만 만들어 두었다.
  - **녹색 범위:** 녹색은 항상 한 위상의 접근로에만 준다.
  - **녹색 종료 조건:**
    - 최소 녹색 min(5 s, 계획 녹색)을 채운다.
    - 그 위상 보행 신호의 정리가 끝나야 한다. 점등 WALK는 단축할 수 있지만 점멸 정리 시간은 다 준다.
    - 그다음 계획된 황색과 전적색을 모두 거친다.
    - 스크램블 위상은 정리 시간이 끝난 뒤에만 떠난다.
    - 제어 중에는 새 WALK를 시작하지 않는다.
  - **기본 플랜 시계:** 선점 중에도 고정 주기 시계는 계속 흐른다. 해제할 때는 같은 안전 규칙으로 녹색을 끝내고, 플랜의 다음 위상이 시작되는 지점에서 기본 플랜으로 돌아간다. 이때 그 교차로의 offset을 영구히 다시 맞추므로 이웃 교차로와의 연동은 깨진다(감수).
  - **요청 처리:**
    - 처리 중인 차량은 정지선을 통과할 때까지 그 교차로를 유지한다. 두 요청 사이를 번갈아 전환하는 것을 막기 위해서다.
    - 요청 범위는 max(150 m, 15 s × 속도)다.
    - 출동 중이거나 이송 중인 차량만 요청한다.
  - **정책:** `ResponsePolicy.preempt?`가 없으면 `reroute`를 따른다. 그래서 UI의 "스마트 대응" 하나가 우회와 선점을 함께 켜고 끈다. 4c1 기록도 그대로 재생된다.
- **편집 시 신호 안전 (모든 모드, 메인 모드 포함 — 4c2-① 후속)**
  - 원래 결함: 편집이나 재컴파일로 신호 계획이 다시 만들어지면 새 계획으로 즉시 바뀌었다. 예를 들어 위상을 역순으로 바꾸면 다음 tick에 N/S 녹색이 바로 E/W 녹색이 되고, N/S 횡단보도가 WALK가 됐다.
  - **계획 식별자(`PlanIdentity.key`)가 바뀐 교차로는 편집 시 정리를 거친다.** 해당하는 경우는 셋이다: 계획이 바뀐 교차로, 신호가 없어진 교차로, 새로 신호가 생긴 교차로.
    - 식별자 구성: 위상 접근로 id, 헤드 차선 id, 횡단보도 id·보행 배정, 녹색·황색·전적색·주기·offset·스크램블.
    - 정리 모듈은 `traffic/signalClearing.ts`이고, 선점 제어도 같은 모듈을 쓴다.
  - **정리 순서:**
    - 녹색이던 것은 계획 황색, 이어서 전적색을 보인다. 편집이 녹색을 끊으므로 최소 녹색은 적용하지 않는다.
    - WALK는 점멸 정리를 전부 준다.
    - 그동안 그 교차로로 들어가는 모든 차선은 진입할 수 없다.
    - 헤드가 없어진 교차로는 황색과 전적색 시간 동안 적색으로 붙잡는다.
    - 그다음 새 계획을 첫 위상 시작에서 시작한다(offset 재설정). 신호가 없어진 교차로는 새 비신호 제어로 넘긴다.
  - **식별자가 같은 재구성은 동작이 그대로다.** 예: 먼 건물·도로, 구간 횡단보도, 폐쇄, 보호구역, 버스 정류장.
  - **골든:** 계획이 바뀌는 편집을 하는 dense grid 트레이스만 tick 900 이후 해시가 바뀌었다(안전한 동작으로 재기록).

### 5. 비교와 KPI (D4)
- **순차 실행:** 같은 시나리오 기록으로 OFF를 먼저 헤드리스 고속 실행해 KPI 시계열을 저장한다. 그다음 ON을 화면에 실행한다. 사용자가 순서나 보기를 바꿀 수도 있다.
- **공정성:**
  - 수요(통행 생성)와 대응 정책은 **RNG 스트림을 분리**한다. 재탐색·대응은 수요 RNG를 소비하지 않는다.
  - 비교는 **같은 sim tick**에서 한다.
- **KPI:**
  - 완료 통행 수
  - 평균 통행시간(완료)
  - **미완료·경로 없음·출발 대기 수**
  - 정체 길이(속도 < 0.3 × 제한속도인 차선 길이)
  - 대응 시간(긴급)
  - 재탐색 차량 수
  - 정전 영향 건물·신호 수
- UI에 "게임 모델, 보정 전 값"을 표시한다.

### 6. 재탐색 (D6)
- **비용과 통행 금지를 분리한다:** 통제 차선은 경로 탐색에서 통행 불가로 다룬다(무한대 대신 제외).
  - **사고 차선은 통행 불가가 아니라 고정 패널티 600 s**(구현 시 변경). 차선 변경 모델이 없어서, 통행 불가로 하면 사고 차선만 목적지인 경우(정류장 차선, 우회로 없는 1차선)가 "경로 없음"이 된다. 우회로가 10분보다 싸면 항상 우회하므로 우회로가 있을 때는 통행 불가와 같은 선택이다. 비용을 더하기만 하므로 A* 휴리스틱은 허용적이다. 목적지가 장애물 앞이면 패널티를 붙이지 않는다.
- **누가 언제 재탐색하는가:** 정보 차량 비율 p(기본 0.7)를 차량 ID 해시로 정한다.
  - 사건이 시작·종료되면 영향 엣지를 경로에 가진 정보 차량을 **안정 순서 큐**에 넣고, tick당 처리 예산(차량 수 고정)으로 처리한다.
  - 벽시계 예산은 쓰지 않는다.
- 재탐색은 현재 차선·방향을 보존하고, 다음 결정 지점부터 경로를 교체한다.
- **무효 경로:** 경로가 단절되면 쿨다운 예외로 즉시 복구를 시도한다. 그래도 경로가 없으면 대기 상태로 두고 KPI의 "경로 없음"에 넣는다. 이는 정보 보유 여부와 무관하다.

### 7. 다양성 (D7·D8, 4b)
- **차량:**
  - 외형 클래스(세단/SUV/해치/밴/소형트럭/택시)는 차량 ID 해시로 정한다. **렌더 전용**이며 sim과 스냅샷은 변경 없다.
  - 클래스별 저폴리 지오메트리는 코드로 생성하고, 인스턴스 색 팔레트를 쓴다.
  - CC0 GLB를 도입한다면 `apps/web/public/assets/LICENSES.md`에 출처를 기록한다.
- **건물:**
  - 외벽 톤 변조는 건물 ID 해시로 하며 **렌더 전용**이다.
  - 성장 프리셋 변형 풀을 확장한다(같은 기능·수요, 외형만 다름). 선택은 lot ID 해시로 **독립 배정**하며 이웃을 참조하지 않는다.
  - 선택 결과는 성장 Command(typeId)에 담기므로 기존 건물은 변하지 않는다.
  - 기존 문서에 새 프리셋을 추가하는 마이그레이션은 DOC_VERSION 5로 한다.

### 8. 시설 (D5, 4c2)
- `BuildingType.service?: 'powerPlant' | 'substation' | 'fireStation' | 'hospital'`. 설계가 기능을 정하며, 같은 설계면 같은 시설이다.
- 용량과 반경은 sim의 기본값 테이블을 쓴다. 문서에는 종류만 둔다.
- 운영 상태(고장·배터리·배전 결과)는 sim 실행 상태다.
- **담당 결정:** 건물·교차로마다 반경 R 안의 가장 가까운 변전소 하나를 담당으로 정한다. 동률이면 ID 순이다. 재분배는 하지 않는다.
- UI에는 "커버리지 기반 공급 모델"이라고 표기한다.
- 필드 왕복(검증·저장·가져오기·docToCommands)을 테스트한 뒤 DOC_VERSION 처리를 확정한다.
- **4c2-① 구현 확정**
  - **기본 설계와 버전:** 기본 시설 설계는 `svc-fire-station`, `svc-hospital`, `svc-substation`, `svc-power-plant` 4종이다(`facilityPresets.ts`). DOC_VERSION 6에서 문서에 없는 id만 추가한다. 기존 "스마트 병원" 템플릿에는 `service`가 없어 시설로 동작하지 않는다.
  - **출동 시설 선택:** 같은 종류 시설 가운데 자유류 A* 비용이 가장 작은 곳에서 출동한다. 동률이면 건물 id가 작은 쪽이다. 시설이 없거나 경로가 없으면 `dispatch.failed`로 남고, 화재는 계속 진행된다.
  - **긴급차량 규칙:**
    - 차량 상한의 예외다.
    - 90 s 정체 제거 대상에서 빠진다.
    - 통행 KPI에 포함되지 않는다.
    - 수요·시민 RNG를 쓰지 않는다.
    - 강제 양보는 없다.
  - **소방차 차종:** 문서에 `fire-truck`이 있으면 그 차종을 쓰고, 없으면 첫 emergency 차종을 쓴다. 골든 해시를 보존하려고 defaults에는 넣지 않았다. 렌더에서는 `ScenarioView.dispatches[].kind`로 구분한다.

### 9. AI 도로 (D9)
- **허용 범위:** "추가 전용"을 **"기존 도로의 연결성과 속성을 보존하는 확장"**으로 재정의한다. 세그먼트 분할은 명시적 예외다.
- **원자 단위:**
  - 도로 한 건은 그 도로에 필요한 노드 생성·분할·세그먼트를 묶은 **하나의 batch 항목**이다.
  - 제안 검토에서 **평탄화하지 않는다.** dry-run은 batch 전체로 하고, 실패하면 그 도로 전체를 제외한다. 독립 도로 사이에서만 부분 성공을 허용한다.
  - 서버 적용도 batch 트랜잭션(기존 `apply/tx`)이라 원자적이다.
- 사용자가 직접 도로를 그릴 때 쓰는 기존 편집 플래너를 그대로 쓴다. 중간 교차·스냅 규칙(고도·교량 포함)을 따르고, 새 ID는 제안 payload에 확정한다.
- 분할로 바뀌는 참조(노선·폐쇄·frontage 등)가 플래너 계약대로 이전되는지 테스트한다.

## 순서
1. **4a:** 스튜디오 조작, AI 위치 표시, AI 설계 표시, 이미지→건물.
2. **4b:** 건물·차량 외형 다양화, 프리셋 변형 풀, AI 도로(9절).
3. **4c1:** 사본 모드 → 입력 계약·재생 → KPI·순차 비교 → 통제 → 사고 → 수요 급증 → 재탐색.
4. **4c2-①:** 시설·출동·신호 선점. **4c2-②:** 정전·배터리.

## 고려했으나 기각
| 제안 | 기각 이유 |
|---|---|
| 서버 임시 룸으로 사본 실행 | 개인 실험 요구와 맞지 않고, 서버 CPU·정리 부담이 생긴다 |
| 사건을 문서 명령으로 | 공유 도시가 오염되고, 스키마 비용이 든다 |
| 사고 = 실제 차량 2대 생성 | 통행 KPI·수요에 섞인다 |
| 앞차 강제 정지로 긴급차 길 비우기 | 차선 변경이 없는 모델에서는 오히려 막힌다 |
| 병렬 비교 기본값 | 메모리·CPU를 실측하지 않았고, 차량 상한 때문에 비교가 왜곡된다 |
| 4b에 동역학 다양성 포함 | 골든 해시와 교차로 점유에 영향이 크다. 후속 과제로 미룬다 |
| 이웃 중복 회피 배치 | 생성 순서에 의존해 결정론이 깨질 위험이 있다 |
