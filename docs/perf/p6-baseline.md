### 측정 환경과 한계
- WSL2 헤드리스 Chromium, ANGLE(GL) → Mesa d3d12 → Windows GPU. 사용한 GPU: **AMD Radeon 내장 그래픽(iGPU)** — ADR §7의 iGPU 장면에 해당.
- RTX 2080 SUPER(데스크톱 GPU)로도 측정했으나, 측정 도중 외부 작업이 그 GPU를 92~100% 점유해 렌더 비용이 100~270 ms로 튀고 한 번은 WebGL 컨텍스트가 소실됐다. 깨끗했던 앞쪽 실행만 참고로 싣는다(§3).
- 다른 에이전트가 같은 기계에서 테스트를 돌리고 있어 CPU 부하가 있었다(load 5~17). 그래서 vsync 상한(60 Hz)을 켜고 정지 교통으로 쟀고, 같은 조건을 교대로 여러 번 반복해 중앙값을 쓴다. vsync를 끈 측정은 수 초짜리 프레임이 섞여 쓰지 않았다.
- 실시간 프레임 시간은 vsync 때문에 16.7 ms에 붙는다. 차이를 보려면 렌더 비용 열을 본다.

### 첫 시도에서 생긴 회귀와 수정
첫 구현(`p6-afterpre-igpu-{1,2}.json`)은 iGPU 렌더 비용이 district 10.8 → 13.1~15.4 ms, 그림자 끔 8.0 → 11.2~12.9 ms로 **나빠졌다**. 원인은 화면 대부분을 덮는 프래그먼트 비용(지면·포장면 노이즈의 sin 해시 여러 번, 깊이 검사 없이 전 화면을 칠하는 하늘 돔, 도로·포장면 아래에서 먼저 칠해지는 지면). 수정:
1. 하늘 돔: 깊이 검사 켜고 불투명 물체 뒤에 그림(renderOrder 3) → 하늘이 보이는 픽셀만 셰이딩.
2. 지면(renderOrder 2)·포장면(1)을 도로·건물 뒤에 그림 → 가려진 픽셀은 깊이 검사에서 일찍 탈락.
3. 노이즈 해시를 sin 없는 산술 해시로, 지면 노이즈 3회 → 2회, 포장면 3회 → 2회.
수정 후 위 표처럼 전과 같거나 낮다.

### 카메라 시점과 측정의 관계
- 측정 포즈(overview·district·street·orbit)는 고정 좌표(`lookAt`)라 자동 맞춤·'도시 보기' 변경(최초 입장 = 밀집 지역 600 m, 두 번째 누름 = 도시 전체)과 무관하다. 시점 정책 변경 후 렌더 비용 재측정은 하지 않았다(렌더 경로 변경 없음).
- 기준 도시에서 시점 정책별 화면 밖 건물(기준점, 16:9): 1차 코드의 도시 맞춤 962/2,000(카메라 뒤 158) → 도시 전체 맞춤 206/2,000(뒤 0, 상한 2 km에 걸림) → 밀집 지역 보기는 의도적으로 지역 밖을 화면 밖·카메라 뒤에 둔다(지역 상자 안 건물은 모두 화면 안, 테스트로 고정).

## 4. 목표 대비
- 검증한 범위: **iGPU(AMD 내장), 정지 차량 약 3,000대**에서 전후 모두 실시간 60 fps(vsync), 렌더 비용은 같거나 감소. 데스크톱 GPU는 첫 시도 코드의 깨끗한 실행 2회(렌더 1~3 ms)뿐.
- **검증하지 않은 것: 데스크톱 GPU에서 최종 코드, 차량 5,000대, 시뮬레이션이 돌아가는(활성) 상태의 60 fps.** 이 문서는 그 조건의 60 fps를 주장하지 않는다.
- **메인 드로 콜 < 150: overview 포즈에서 전(169)부터 이미 초과**, 후 171. 원인은 도시 전체가 보일 때의 도로 청크(256 m, 청크당 1콜, 이 장면에서 약 120개)와 건물 설계별 메시. P6c-1 변경분은 +2. 도로 청크 크기·건물 대구역화는 P6c-2(측정 후 결정) 과제로 남긴다.
- 악화 금지: 그림자 패스·삼각형·렌더 비용 모두 감소, 메인 드로 콜 +2.

## 5. 편집 후 갱신 비용(새 파생 데이터)
도로·건물·필지 명령이 확정될 때만 다시 계산하며(dirty, 프레임당 1회로 합침) 포인터 이동 중에는 계산하지 않는다. 협업자의 명령도 같은 전체 재생성 경로를 탄다. 기준 도시(2,000동·도로 1,012개) 기준:

| 대상 | 측정 | 값 |
|---|---|---|
| `pavingShapes()`(다각형만) | 1차 문서의 값, 부하 낮을 때 | 약 4 ms |
| `pavingShapes()` | Sol 리뷰, 병행 테스트 부하 | 7.4~11.9 ms |
| **`PavingLayer.update()`**(삼각분할·버퍼 생성 포함, 1차 코드) | Sol 리뷰, 병행 테스트 부하 | **16.4~64.8 ms** |
| `pavingShapes()` / `PavingLayer.update()`(최종 코드: 포장 블록 안 건물의 앞마당 생략) | executor, Node, load avg 34, 10회 | 중앙값 6.6 ms / **중앙값 15.2 ms, 4.1~27.4 ms** |

- 1차 문서의 "약 4 ms"는 다각형 계산만이고 편집 후 실제 갱신 비용(`PavingLayer.update`)을 대표하지 않았다. 큰 도시에서 편집 한 번마다 한 프레임(수십 ms)이 늦을 수 있다.
- 남은 개선(후속): 변경된 블록만 다시 만드는 증분 갱신 또는 청크 분할. 지오메트리 속성 배열 약 0.48 MB(Sol 측정, 1차 코드). 반복 편집 시 GPU 메모리 누수는 미검증(교체·종료 시 dispose는 확인).
