## 요약 (5줄 이내)
1. 초보가 쉽게 창의적으로 만드는 도구의 공통점은 **"3D 객체를 직접 클릭 → 고스트 미리보기 → 확정" + "스냅 격자 안에서는 뭘 해도 어느 정도 예쁘다" + "세부(모서리·창·지붕)는 규칙이 자동 결정" + "부담 없는 되돌리기"** 이다.
2. 권장: **2m × 2m × 1층(3.2m 기본) 복셀 셀을 3D에서 클릭/드래그로 쌓고, 저장 시 층별 점유 영역을 직교 다각형 BuildingPart 여러 개로 변환**한다. 현재 서버 검증(꼭짓점≤32, 구멍 없음, 볼륨 겹침 금지, 파츠≤16)과 호환된다 [코드]. 단, **파츠 16개 상한과 파츠당 색 1개**가 병목이라 병합·색 규칙을 설계에 넣어야 한다.
3. 창의성은 셀보다 **장식 부품(prop) + 파사드/지붕 프리셋 + 색 팔레트 + 대칭 + 주사위(랜덤 시드)** 에서 나온다. prop은 `BuildingType.props[]`(종류 enum + 격자 앵커 + 회전 + 색)로 추가하고 렌더는 기존 건물 지오메트리 굽기에 합친다.
4. 오픈소스 코드는 거의 쓸 게 없다(three.js voxel painter 예제 MIT가 유일하게 직접 참고 가능). **Townscaper식 WFC 자동 형태는 MVP에서 제외**, 규칙 기반 소규모 자동화(코너/층 경계 마감)만 둔다. 무료 에셋은 Kenney(CC0)가 라이선스상 안전하다.
5. 가장 큰 위험은 (a) 셀 데이터를 저장하지 않는다는 ADR 0007 §5와의 충돌(역변환 손실), (b) 파츠 상한·색 해상도, (c) 3D 피킹·카메라 UX 난이도. 실행 전 ADR 개정 결정이 필요하다.

## A. 현재 구조 (코드 확인) [코드]

- `BuildingType{id,name,zone,parts[],smart?,rev?}`, `BuildingPart{offset,width,depth,floors,floorHeight,baseHeight,roof,color,roofColor,footprint?,use?,facade?}` — `packages/shared/src/model.ts`.
- `footprint`는 직교 다각형(구멍 없음, 꼭짓점 ≤ 32, 건물 로컬 좌표). 다각형 파츠는 **평지붕만** 가능. `gable`/`pyramid`는 사각형 파츠만. 파츠 ≤ `LIMITS.buildingParts = 16`, 같은 건물 내 볼륨의 체적 중첩 금지, 층 1..200, 층고 2..12 — `apply.ts`, ADR 0007.
- 색은 **파츠 단위**(`color`, `roofColor`). 셀 단위 색은 현재 표현 불가.
- 저장은 `buildingType.upsert` 한 개 명령 + `expectedRev` 낙관적 동시성. 편집은 로컬 초안, 저장 시 `preflight`로 서버와 동일 검증 — `designDraft.ts`.
- ADR 0007 §5: "셀은 편집 표현일 뿐 **저장하지 않음**". §Phase 2b 연기 목록에 "전용 3D 스튜디오(푸시/풀 기즈모), 되돌리기/다시하기"가 이미 있음 — 이번 작업은 그 항목의 구체화다.
- 기존 에디터: 평면 캔버스(`FootprintPainter`, 셀 1/2/4m), 부지 40~160m(`PLOTS`), 3D는 미리보기(`PartPreview`)뿐.
- 렌더: 설계(타입)별 지오메트리를 한 번 굽고 타입별 InstancedMesh, 파사드는 정점 속성 셰이더 — `render/buildingGeometry.ts`. three 0.186 사용.

즉 "쉬움"의 병목은 모델이 아니라 **입력 방식(2D 칠하기 → 숫자 → 다시 3D 확인)의 왕복**이다. 3D에서 직접 만들고 같은 3D에서 결과를 보게 하는 것이 핵심 개선이다.

## C. 공통 패턴 Top 8 ("쉬움 + 창의성"을 만드는 것)

1. **3D 객체를 직접 조작하고, 결과가 같은 화면에 즉시 보인다** (Townscaper, Minecraft, Sims, voxel painter). 평면/숫자를 따로 보고 다시 3D로 가는 왕복이 가장 큰 진입장벽. → 편집 뷰 = 결과 뷰.
2. **고스트 미리보기 + 가능/불가능 색** (voxel painter 예제의 rollOver, Fortnite/Valheim). 클릭 전에 결과를 알 수 있어 두려움이 없다.
3. **스냅 격자가 미적 품질을 보장**한다 (LEGO 스터드, Townscaper, Minecraft). 선택지를 줄여서 쉬워지고, 그 안의 조합으로 창의성이 나온다.
4. **세부는 규칙이 결정**한다 (Townscaper 코너/아치, Sims 지붕 자동, 창은 벽에만 놓임). 사용자는 "덩어리"만 결정. → 우리: 모서리 마감, 최상층 지붕, 1층 상점/로비를 자동 기본값으로.
5. **고정된 작은 팔레트와 개별 색 교체** (LEGO, MagicaVoxel, Townscaper). 색이 조화되도록 큐레이션하면 초보 결과가 좋아 보임.
6. **대칭/미러/복제** (Spore, MagicaVoxel, Sims 방 복사). 입력 한 번에 효과 2배 이상, 결과가 정돈되어 보임.
7. **시작점 제공: 프리셋·랜덤(주사위)** — 빈 캔버스 공포를 없앰. "무작위 → 마음에 드는 것 하나를 고쳐 쓰기" 흐름. [Townscaper의 랜덤성은 [미검증]이나 일반 패턴]
8. **부담 없는 되돌리기와 단계적 복잡도** (SketchUp 푸시/풀 → 숫자 입력은 선택, Sims 자동 지붕 → 수동 조정). 간단 모드로 시작해 필요할 때 세부 패널을 연다.

보조 패턴: 층 슬라이더로 한 층씩 편집(Sims/Bloxburg), 낮/밤·거리 맥락에서 보기(결과 만족도), 완성품 공유(우리는 팀 도시에 바로 배치).

## D. 선택지 비교: 편집 표현

| 선택지 | 장점 | 단점 | 사례/근거 |
|---|---|---|---|
| (1) **복셀 셀 3D 편집 → 저장 시 BuildingPart 변환** | 가장 쉬움. 서버 검증 계약 변경 없음(꼭짓점/겹침/파츠 한도로 변환 후 기존 `buildingType.upsert`). 기존 파츠·파사드·지표(`designStats`)·렌더 재사용 | 변환 손실(셀 단위 색/지붕은 파츠 단위로 뭉개짐), 파츠 ≤16 병목, 역변환 필요 | Townscaper/Minecraft/MagicaVoxel |
| (2) 파츠(박스) 직접 조작 + 면 푸시/풀 기즈모 | 데이터 모델과 1:1. 정밀. 변환 없음 | 초보에게는 기즈모·핸들이 어려움. L자·계단식 같은 모양은 박스 여러 개를 직접 조합해야 함 | SketchUp, Roblox Studio |

| (4) 벽 그리기 → 방/지붕 자동(Sims식) | 건축 느낌 | 벽 두께·내부·창 흡착 등 모델 확장이 큼. 우리는 "외관 매스"라 과함 | Sims 4 |

## E. 권장 스튜디오 설계

### E-1. 셀 크기와 좌표
- **수평 2m × 2m, 수직 1층 = 1셀**. 층고는 건물(또는 파츠) 단위 값(기본 3.2m, 허용 2..12는 서버 범위). 근거: 기존 에디터 격자 1/2/4m 중 2m가 중간값이고 기본이 2m [코드], 12×10m 기본 파츠가 6×5셀로 손에 잡히는 크기. 4m 셀은 거칠고 1m는 셀 수가 폭증(아래 성능).
- "큰 브러시" 옵션으로 2×2(=4m) 한 번에 칠하기를 제공하면 4m 해상도 요구도 충족된다. 1m는 MVP에서 제외.
- 편집 범위: 기본 부지 60m(±30m) 안에서 **셀 가로 최대 24×24(48m), 최대 20층** 정도로 제한 [제안, 코드 상한은 폭 300·200층이지만 UX/성능 상한을 따로 둠]. 부지 `PLOTS`의 40~160m 선택은 유지 가능하나 MVP는 60m 고정을 권장.
- 좌표: 건물 로컬 (i, j, k) → x = i·2, z = j·2, 층 k. 원점 정렬은 기존 `cellKey`/`outlineToCells`/`cellsToOutline` 유틸 재사용 가능 [코드].

### E-2. 복셀 → BuildingPart 변환 (타당성: 타당함, 단 규칙이 필요)
알고리즘 개요:
1. 층 k마다 점유 셀 집합 S_k를 구한다. 연결 성분(4-이웃)별로 분리한다.
2. 연속된 층에서 **같은 점유 + 같은 벽색 + 같은 파사드 + 같은 용도**이면 하나의 파츠로 합친다(`floors = n`, `baseHeight = 시작층 × floorHeight`). 탑이 위로 올라갈수록 좁아지는 건물은 파츠가 층 구간별로 나뉜다.
3. 각 성분을 `cellsToOutline`로 직교 다각형화한다. 구멍(중정)은 서버가 금지 [코드] → **자동 분할**: 구멍이 있으면 행/열 방향 절단선으로 구멍 없는 2~4개 파츠로 쪼갠다(Sims식 "그냥 칠했는데 되게 하기").
4. 꼭짓점 > 32이면 저장 불가로 두고 UI에 경고 + 문제 위치 하이라이트. 또는 다각형을 둘로 분할.
5. 겹침 금지 규칙: 서로 다른 층 구간이 **같은 높이대에서 겹치지 않으므로** 구조적으로 안전. 같은 층 안에서 분리 성분은 겹치지 않음.
6. 허공 위에 떠 있는 셀(오버행)은 `baseHeight`로 표현 가능. 허용하되 "지지 없음" 안내(옵션: 필로티 1층 `ground:'pilotis'`와 연결).

**병목 3가지** (그리고 대응):
- **파츠 ≤ 16**: 복잡한 형태는 쉽게 초과. 대응: 병합을 최대화(2번), 용도·파사드·색이 다른 셀은 다른 파츠가 되므로 **복셀 단위 색/파사드는 MVP에서 금지하고 "층 덩어리 단위 스타일"** 로 제한. UI에 "파츠 8/16" 같은 예산 게이지(숫자 입력 없이 항상 표시)로 피드백.
- **파츠당 색 1개**: 셀별 색칠이 Townscaper/MagicaVoxel의 즐거움이지만 모델이 못 받는다. 선택지: (a) MVP는 "층 덩어리 단위" 색(= 같은 연결 성분·같은 층 구간 선택 후 색) 또는 면(벽/지붕) 두 색, (b) 후속으로 `BuildingPart`에 벽 색 팔레트 인덱스 + 하단 띠(base band) 같은 규칙 추가, (c) 장기적으로 `voxels` 원본 저장(아래 E-6) 후 정점 색으로 굽기. (a)가 MVP, (c)가 모델 변경이므로 ADR 개정 필요.
- **다각형 파츠는 평지붕만** [코드]: 박공/피라미드 지붕은 사각형 파츠에만. 대응은 E-4.

타당성 결론: **셀 → 파츠 변환은 기존 서버 계약을 건드리지 않고 가능**하며, 사용자가 볼 때 "클릭으로 쌓는" 경험을 줄 수 있다. 다만 "셀 단위 색칠"과 "자유 지붕"은 모델 확장 없이는 제한되므로 MVP의 표현 자유도를 먼저 합의해야 한다.

### E-3. 장식 부품(prop) 데이터 구조
제안 (`BuildingType`에 선택 필드 추가, `DOC_VERSION` 증가 없이 optional 추가는 `normalizeDoc`의 `??=` 패턴으로 호환 가능 [코드]):

```ts
type PropKind =
  | 'balcony' | 'awning' | 'sign' | 'ac' | 'chimney' | 'antenna' | 'water_tank'
  | 'flag' | 'planter' | 'pergola' | 'skylight' | 'dish' | 'pipe';   // 폐쇄 enum, 임의 메시 금지

interface BuildingProp {
  id: string;                 // 짧은 id, 건물 내 유일
  kind: PropKind;
  /** 건물 로컬 격자 앵커: 셀 좌표(2m) 중심. 벽 prop은 face로 방향 결정 */
  cell: { i: number; j: number };
  floor: number;              // 어느 층 바닥 기준 (0..floors-1), 옥상 prop은 -1 = 옥상면
  face?: 0 | 1 | 2 | 3;       // 벽 부착 방향(+x,+z,-x,-z). 옥상 prop은 rot 사용
  rot?: 0 | 1 | 2 | 3;        // 90° 단위
  size?: 1 | 2 | 3;           // 1~3 셀 폭(간판·차양)
  color?: string;
  text?: string;              // 간판 문자 (길이 ≤ 12, 렌더에서 캔버스 텍스처 아틀라스)
}
```
- 상한: 건물당 **props ≤ 64**, 서버 검증: kind enum, 앵커가 해당 층 점유 셀의 외곽 면에 접하는지(벽 prop) 또는 최상층 점유 셀 위인지(옥상 prop), `text` 길이.
- **저장 위치**: 셀 앵커(i,j,floor)는 복셀에 종속되므로, 파츠 변환 후에도 유효하려면 저장 시 `x,z`(미터), `y`(미터)로 **환산**해서 저장한다. 그러면 모델이 셀에 의존하지 않고(ADR 0007 §5 유지) 역변환 시 재스냅한다. 권장: 저장 형식은 `pos:{x,y,z}`(미터, 0.5m 해상도) + `rot` + `face`, 에디터가 셀로 보여줌.
- 기존 `SmartFeatures`(`solarRoof`, `greenRoof`, `evChargers`, `sensors`, `dronePort`)는 **옥상 면적 예산**을 공유한다 [코드]. 옥상 prop(antenna, water_tank, dish 등)은 면적을 소모하므로 같은 예산(`roof equipment exceeds`)에 포함할지 결정 필요 → 권장: 작은 prop은 면적 0.5㎡씩 환산하여 합산하거나 예산 제외 중 택1(결정 필요).
- 충돌: prop은 도로 침범 검사에서 **벽 면에서 최대 +1.5m(발코니·차양)** 까지만 허용하고 지표(건폐율)에는 포함하지 않음. 도로 침범은 prop 돌출을 포함해 검사할지 결정 필요(단순히 `setback`에 흡수 권장).
- 렌더: 기존 건물 지오메트리 굽기(`buildingGeometry`)에 prop 박스/간단 메시를 함께 병합. prop 수 ≤64이므로 지오메트리 증가는 작고 InstancedMesh 구조에 영향 없음. Kenney CC0 모델은 단순화(저폴리) 후 prop 템플릿으로 사용 가능하나 GLB 로더 의존성이 늘므로 **MVP는 프리미티브(박스/원기둥/삼각기둥) 조합 prop**을 권장.
- 협업: prop 편집도 초안 안에서 일어나고 저장 시 `buildingType.upsert`에 포함 → 기존 `expectedRev` 충돌 모델 그대로.

### E-4. 지붕 형태
현 제약: 다각형 파츠 평지붕만 [코드]. 선택지:

| 선택지 | 내용 | 비용 | 평가 |
|---|---|---|---|
| R1. 평지붕 + 옥상 prop(옥상 정원, 태양광, 헬리패드, 안테나) | 기존 그대로 | 최소 | **MVP**. 스마트시티 주제와도 맞음 |
| R2. 최상층 사각형 영역을 최대 사각형들로 분해해 각 사각형을 `gable`/`pyramid` 파츠로 변환 | 모델 변경 없음 | 중. 파츠 수 증가, 모서리 이음새 어색 | MVP 후보(제한적: 사각형 최상층에서만 박공 허용 → "지붕 종류" 선택은 사각 매스에서만 활성) |
| R3. 다각형 파츠에 `roof: 'hip'|'gable'` 허용(스트레이트 스켈레톤 또는 직교 L/T 전용 규칙) | 모델·서버·렌더 변경 | 큼 | 후속. 직교 다각형 전용 간이 알고리즘(셀 기반 계단형 "스텝 지붕")이 현실적일 수 있음 [제안, 미검증] |
| R4. 셀별 지붕 블록(경사 셀) | Townscaper식 | 모델 확장 필요 | 후속/보류 |

권장: **MVP는 R1 + 사각 최상층에 한정한 R2**. 사용자에게는 "지붕: 평지붕/박공/피라미드" 한 선택지로 보이고, 불가능한 형태에서는 비활성 + 이유 툴팁.

### E-5. 재질/색 팔레트와 스타일 프리셋
- 팔레트: **벽 12색 + 지붕 6색 + 포인트 6색 정도의 큐레이션 고정 팔레트** (LEGO/MagicaVoxel 패턴). 자유 색 선택(#hex)은 "고급"에 숨김. 서버는 이미 `color` 형식 검증 [코드] → 팔레트는 클라이언트 상수.
- 재질: 현재 파사드 셰이더(grid/ribbon/curtain/none, windowRatio, ground) [코드]로 벽 질감을 대체하므로 **"파사드 스타일 프리셋"** 이 곧 재질 선택: 예) "벽돌 주택"(grid, 0.3, shop 없음), "유리 오피스"(curtain, 0.85), "상가 건물"(grid 0.5 + ground shop), "현대 주택"(ribbon). 프리셋 = (벽색, 지붕색, 파사드, 층고, 옥상 prop 세트) 묶음.
- 스타일 프리셋은 팀 공유를 위해 기존 건물 타입 프리셋 JSON 패턴(`SMART_CITY_PRESETS`) [코드]을 재사용.

### E-6. 랜덤 생성기 ("주사위")
- 입력: 시드(정수), 스타일 프리셋, 대략 크기(작음/중간/큼), 용도.
- 규칙(경량 형상 문법, CGA의 부분집합): ① 기단(1~2층, 넓게) + ② 본체(기단 대비 70~100% 폭) + ③ 상층 후퇴(setback) 0~2단계 + ④ 최상층 지붕 종류 + ⑤ 옥상 prop 0~3개 + ⑥ 발코니/차양을 파사드 확률로 부착.
- **결정적**: 시드 → 같은 결과. 클라이언트 로컬에서 초안으로 생성하고 저장은 일반 `upsert` → 서버/협업 영향 없음. 시드를 건물 이름이나 메타에 기록하면 "같은 시드 공유"도 가능.
- 주사위 결과는 항상 "초안에 반영"이며 되돌리기 가능해야 한다. 한 번 더 누르면 다른 시드.
- 구현 부담은 작다(순수 함수 + 단위 테스트 가능). 03 보고서 결론("CGA 전체 구현은 과함, 부분집합은 가치")과 일치.

### E-7. 대칭, 되돌리기, 협업 구조
- **대칭**: 에디터 상태로 X축/Z축 미러 토글(셀 배치 시 거울 위치도 함께 변경). 모델 변경 없음.
- **되돌리기/다시하기**: 편집이 **로컬 초안**이므로 로컬 스택(셀 변경 diff)으로 구현 가능 — 협업 명령 로그와 독립 [코드: 초안 구조]. ADR 0007이 연기한 "되돌리기/다시하기"는 도시 전체 레벨이고, 건물 스튜디오 초안 단위는 별개로 MVP에 포함 가능.
- **저장**: 기존 `buildingType.upsert` + `expectedRev`. 한 건물을 동시에 둘이 실시간 공동 편집하는 기능은 MVP 범위에서 제외(복잡). 대신 협업 UX 9번(다른 사용자가 편집 중인 객체 표시) [코드/ADR]를 건물 타입에도 적용: "A가 이 설계를 편집 중" 배지 + 충돌 시 복제 저장.
- **ADR 0007 §5 충돌 지점**: 셀을 저장하지 않으면, 이미 저장된 건물을 다시 열 때 **파츠 → 셀 역변환**이 필요하다. 2m 격자에 정렬된 파츠(= 스튜디오로 만든 것)는 무손실. 정렬되지 않은 기존 프리셋(예: 폭 11m)이나 다른 경로로 만든 파츠는 가장 가까운 격자에 스냅되어 모양이 바뀐다. 선택지:
  - (A) **셀 미저장 유지**(권장 MVP): 역변환은 2m 스냅 + 변경 시 경고 배너("모양이 2m 격자에 맞춰집니다, 복제본으로 편집"). 구 에디터는 "고급 모드"로 유지해 정밀 조정 가능.
  - (B) `voxels` 원본 저장(런길이 인코딩, 상한 예: 셀 2,000개): 색/지붕 셀 단위 확장 가능, 단 파츠와 불일치 위험(서버가 파츠로부터 검증 가능한 것은 파츠뿐) → ADR 개정 + 검증 규칙 필요. 후속.

### E-8. 성능 (셀 수 상한)
- 편집 중 렌더: 점유 셀을 **InstancedMesh(박스 1개)** 또는 면 병합 메시로 그린다. 상한 24×24×20 = 11,520 칸이어도 실제 점유는 대개 수백~수천. 인스턴스 수천은 모바일급이 아닌 한 문제없다 [일반 지식, 미검증: 실측 필요].
- **편집 UX 상한 제안: 점유 셀 ≤ 2,000, 층 ≤ 20, 평면 ≤ 24×24**. 근거는 파츠·꼭짓점 상한(16/32)이 이미 복잡도를 제한한다는 점이며 [코드], 실측 후 조정.
- 피킹: 지면 격자 + 점유 셀을 **그리드 DDA 레이 순회**로 구현(three.js `Raycaster` 대신). 한 번에 수십 셀만 검사하므로 `three-mesh-bvh` 불필요. 대규모(수만 셀)가 필요해질 때만 도입.
- 도시 렌더 영향 없음: 도시 씬에는 변환된 BuildingPart 지오메트리만 들어가며 타입별 InstancedMesh 구조 유지 [코드]. 파츠 수가 늘면 타입당 지오메트리가 커지지만 16 상한이 있다.
- 변환/검증은 `preflight`(서버와 동일 로직) 호출. 편집마다 호출하면 낭비이므로 **debounce 150ms** 후 실행 [제안].

## F. 권장안 (MVP / 후속)

### MVP (스튜디오 1단계)
1. **3D 스튜디오 뷰**: 오빗 카메라 + 지면 격자(2m). 클릭 = 셀 추가(면 법선 방향 또는 지면), 우클릭/Shift = 삭제, 드래그 = 선/면 채우기. 고스트 미리보기(가능=초록, 불가=빨강). [voxel painter 패턴 참고, 소스 검증]
2. **층 슬라이더/현재 층 강조**(위층 반투명). 층 복제("이 층을 위로 N층").
3. **Undo/Redo(로컬)**, **대칭 토글(X/Z)**.
4. **자동 마감 규칙**: 최상층 지붕 자동, 1층 기본 파사드(상점/로비 선택), 모서리 마감은 셰이더 기본 처리.
5. **스타일 프리셋 + 고정 팔레트**(벽/지붕 색). 층 덩어리 단위 색.
6. **prop 6~8종** 프리미티브: 발코니, 차양, 간판(문자), 에어컨, 안테나, 물탱크, 굴뚝, 플랜터 + 기존 스마트 설비(태양광/옥상 정원/드론 포트)를 같은 "옥상" 패널에서 조작.
7. **주사위**(시드 + 스타일 + 크기).
8. **저장**: 셀 → 파츠 변환 → `preflight` → `buildingType.upsert`(`expectedRev`). 파츠 예산 게이지, 오류는 위치 하이라이트.
9. 구 에디터(숫자 입력)는 "고급 모드"로 유지.

### 후속
- 면 푸시/풀 기즈모(파츠 직접 조작), 셀 단위 색/지붕 블록(`voxels` 원본 저장 ADR 개정), 다각형 파츠 지붕(R3), 실시간 공동 편집(명령 단위 `voxel.set` 로그), Kenney 기반 모델 prop, 파사드 규칙(층 그룹 반복), 시나리오 템플릿 갤러리/갤러리 공유, 낮/밤·거리 맥락 프리뷰.

## 위험과 미해결 질문

위험:
1. **ADR 0007 §5(셀 미저장)와의 긴장**: 재편집 시 역변환 손실. MVP는 (A) 경고 + 복제 편집으로 수용할지, (B) 개정할지 Lead 결정 필요.
2. **파츠 16개 상한/파츠당 색 1개**: 복잡한 창작물이 저장 불가가 되면 "창의성" 목적이 훼손된다. 상한을 올릴 수 있는지(서버 성능·메시 크기) 확인 필요. 근거 없이 상한을 올리는 것은 위험 — 지오메트리 병합 비용을 실측할 것.
3. **3D 편집 UX 난이도**: 피킹, 오빗 vs 클릭 충돌(ADR의 5px 임계값 패턴 재사용 가능 [코드]), 모바일/터치 대응. 스튜디오가 새로운 어려움을 만들 수 있으므로 사용자 테스트(초보 3~5명) 필요.
4. **서버 규칙과 UI 판정 불일치**: 변환 결과가 서버에서 거부되면 사용자가 원인을 이해하지 못함 → `preflight` + 위치 하이라이트로 완화.
5. **라이선스**: Goxel/Sweet Home 3D 계열(GPL) 코드 복사 금지, 라이선스 없는 Townscaper 클론 참조 금지. Kenney CC0만 자산 소스로 안전.
6. **범위 팽창**: 셀 색, 지붕 블록, WFC 자동 형태는 모두 모델 확장을 요구한다. MVP를 "층 덩어리 단위 스타일 + prop + 주사위"로 못 박을 것.
7. **prop 텍스트(간판)**: 임의 문자열 입력 → 길이/문자 집합 제한, 욕설·악용은 팀 협업 도구이므로 수준만 검토.
