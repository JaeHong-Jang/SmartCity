# Research: 보행자·시민 활동 시뮬레이션과 횡단 시설·교통 정온화 통합

## 요약

- 보행 그래프를 기존 도로 컴파일 결과에서 파생하되, 차량용 `Lane/Connector`와 별도 타입으로 관리한다.
- MVP 이동은 **경로 추종 + 방향별 보행 띠 + 선행자 간격 제한**, 시민 활동은 **지속되는 개인 ID와 연속된 통행 일정**으로 구현한다.
- 횡단 안전은 차량·보행자가 공유하는 **충돌 구역의 원자적 예약**으로 보장하고, 보행 신호는 `WALK → CLEARANCE → RED`로 분리한다.
- 과속방지턱·속도구역은 경로상의 속도 제약, STOP·횡단보도는 내부 정지선 제약으로 통합한다.
- 차량 3천 대·보행자 5천 명에서 `step < 4ms`는 **미검증 목표**다. 경로 탐색 예산·지역 인덱스·버퍼 재사용이 전제다.

### 2. 보행 네트워크: 도로 기하에서 파생

**MVP 자료구조**

```ts
type PedEdgeKind = 'sidewalk' | 'corner' | 'crossing' | 'access';

interface PedEdge {
  id: string;
  kind: PedEdgeKind;
  from: number;
  to: number;
  points: Vec2[];
  cum: number[];
  length: number;
  width: number;
  crossingId?: string;
}

interface PedGraph {
  nodes: PedNode[];
  edges: PedEdge[];
  outgoing: number[][];
  buildingAccess: BuildingAccess[];
  stopAccess: StopAccess[];
}
```

물리적인 보도 하나에 양방향 이동을 허용하되, 경로 탐색에서는 양방향 인접 관계를 만든다. 차량의 일방통행 여부는 보행 방향을 제한하지 않는다.

**보도 중심선**

현재 `shared/src/roads.ts`는 보도 폭을 `SIDEWALK_WIDTH = 2.5m`로 정의한다. 도로 외곽 폭을 보도 중심선 오프셋으로 사용하면 사람이 보도 바깥을 걷는다.

```text
carriagewayWidth = (lanesForward + lanesBackward) × laneWidth
sidewalkCenterOffset = carriagewayWidth / 2 + sidewalkWidth / 2

rightSide = offsetPolyline(trimmedCenterline, +sidewalkCenterOffset)
leftSide  = offsetPolyline(trimmedCenterline, -sidewalkCenterOffset)
```

현재 폭 정의의 근거는 [도로 기하 유틸](/mnt/c/Users/User/Desktop/대학교/3학년/스마트시티%20프로젝트/packages/shared/src/roads.ts:1)이다.

**컴파일 순서**

1. 기존 도로 컴파일에서 짧은 세그먼트 보정까지 끝낸 최종 setback을 얻는다.
2. `sidewalk=true`인 세그먼트 양쪽에 보도 엣지를 만든다.
3. 노드에 접속하는 도로 팔을 바깥쪽 접선 각도순으로 정렬한다. 동률은 segment ID로 정한다.
4. 각 인접 도로 팔 사이에 모서리 노드와 보행 연결을 만든다.
5. 각 도로 팔의 양쪽 모서리를 횡단보도로 연결한다.
6. 건물 출입구·버스 정류장의 접속점을 삽입한다.
7. ID순으로 dense index를 부여하고 연결 성분·충돌표·공간 인덱스를 생성한다.

**모서리는 교차로 중심을 통과하면 안 된다.** 인접 보도 경계의 연장선 교점 또는 제한된 곡선으로 연결하고, 차도 영역 침범을 검사한다. 예각에서는 miter 길이를 보도 폭의 2배 정도로 제한하고 bevel로 전환한다. 이 값은 기하 안정성을 위한 제안값이다.

교차로마다 전부 연결하는 방식도 피한다. 차도를 건너는 연결은 반드시 `crossing` 엣지여야 한다.

**자동 횡단보도**

- MVP: 보도가 있는 3지 이상 교차로의 각 도로 팔에 생성한다.
- 거의 일직선인 2지 연결은 같은 쪽 보도를 이어주며, 횡단보도는 명시적으로 설치한다.
- 보도 없는 도로·고속도로 성격 도로는 자동 생성 대상에서 제외한다.
- 자동 시설은 문서에 대량 저장하지 않고 파생한다. 사용자가 비활성화하거나 설정을 바꾼 부분만 override로 저장한다.
- 설치 위치는 차량 정지선과 일관되어야 한다. 횡단보도가 기존 차선 위에 놓이면 그 차선에도 내부 정지선을 생성한다.

**건물 출입구 연결**

건물 중심 대신 `Building.entranceLocal`을 두고 `rotation`으로 월드 좌표를 계산한다. 미지정 건물은 도로를 향한 외곽면에서 출입구 후보를 결정한다.

```text
candidates = 가까운 보도 공간질의(출입구, 최대 80m)

후보를 (접속 거리, 보도 ID, 접속 s)순으로 검사:
    연결선이 다른 건물·차도·금지 영역을 통과하면 제외
    통행 가능한 첫 후보에 access edge 생성

후보 없음:
    buildingAccess = disconnected
```

80m는 현재 차량 수요의 접속 반경을 재사용하는 초기값이다. 가장 가까운 보도라도 반대편 차도 너머라면 직접 연결하지 않는다. 막힌 경우 미접속으로 집계하고, 후속으로 대지 내부 보행 경로를 찾는다.

접속 위치는 도로 원본 호 길이의 `u=s/L`로 정규화해 저장하고, 각 오프셋 곡선에 기하적으로 대응시킨다. **차량 차선·보도의 잘린 길이에 같은 비율을 곱하는 근사**는 출입구와 정류장 정렬 오차를 만들 수 있다.

### 3. 보행자 이동: 경로 추종과 보행 띠

**MVP 수치**

| 항목 | 제안값 |
|---|---:|
| 물리 갱신 | 20Hz, `dt=0.05s` |
| 신체 반경 | 0.25m |
| 보행 띠 폭 | 0.65m |
| 보도 가장자리 여유 | 각 0.25m |
| 같은 띠 최소 중심 간격 | 0.70m |
| 자유 보행속도 | 평균 1.30m/s, 범위 0.80~1.80m/s |
| 좁은 보도 | 한 방향씩 통과시키는 구간 예약 |

자유 보행속도는 시민 생성 시 한 번만 뽑는다. 정규분포가 꼭 필요하지 않으므로 시드 RNG 두 번으로 대칭 삼각분포를 만들 수 있다.

```text
vPreferred = clamp(1.30 + 0.50 × (rng.next() - rng.next()),
                   0.80, 1.80)
```

평균 1.2~1.4m/s 범위는 초기 설정 범위로 사용한다. **한국 시민 전체의 실측 분포로 검증된 값은 아니다.** 신호 설계속도 1.0m/s와 개인 자유 보행속도는 구분한다.

현재 2.5m 보도에서 가장자리 여유를 빼면 0.65m 띠 세 개가 들어간다. MVP는 각 방향에 한 개씩 고정 배정하고 중앙 띠는 비워 둔다. 후속에서 중앙 띠를 결정적 추월·회피에 사용한다.

```text
각 띠의 보행자를 진행 방향의 s, personId순으로 유지

previousState 기준:
    desiredAdvance = vPreferred × dt
    allowedAdvance = 선행자까지 거리 - minimumSpacing
    nextS = s + max(0, min(desiredAdvance, allowedAdvance))

엣지 끝에 도착:
    다음 엣지 입구 공간과 통행 권한이 있으면 전이
    없으면 끝에서 대기
```

엣지 전이는 목적 띠의 공간을 원자적으로 예약한다. 모서리에서는 각 엣지만 검사하면 서로 다른 보도에서 들어온 사람이 겹칠 수 있으므로, 소규모 합류 예약이나 0.65m 대기 셀을 추가한다.

측방 오프셋은 렌더링 장식만으로 처리하지 않는다. 모델이 허용한 띠 중심을 따라야 하며, 임의 흔들림이 보도 경계나 다른 띠를 침범해서는 안 된다.

**Social force를 후속으로 두는 이유**

대표식은 다음과 같다.

\[
\frac{d\mathbf v_i}{dt}
=
\frac{v_i^0\mathbf e_i-\mathbf v_i}{\tau}
+\sum_j\mathbf f_{ij}
+\sum_W\mathbf f_{iW}
\]

희망속도 복귀항과 보행자·벽의 상호작용으로 군중 흐름을 표현한다. [Helbing·Molnár 원논문](https://doi.org/10.1103/PhysRevE.51.4282)

5천 명을 전수 비교하면 틱당 약 1,250만 쌍이다. 공간 해시를 쓰면 통상 `O(Pk)`로 줄지만, 고밀도에서는 이웃 수와 적분 안정성 문제가 남는다. 결정적 구현도 가능하지만 이웃 정렬·고정 적분·접촉 보정이 필요하다. 향후 광장·대피 시뮬레이션에 국소 적용하고, 일반 보도에는 단순 모델을 유지하는 안을 권장한다.

| 주거 | 30㎡/인 |
| 사무 | 20㎡/일자리 |
| 상업 | 40㎡/일자리 |
| 산업 | 60㎡/일자리 |
| 공공 | 50㎡/일자리 |
| 취업 인구 비율 | 55% |

새로운 상충 계수를 만들지 말고 `buildingMetrics.areaByUse`와 공유한다. 이 계수는 저장소 주석상 **보정된 한국 실측치가 아닌 게임값**이다. [기존 도시 지표 계수](/mnt/c/Users/User/Desktop/대학교/3학년/스마트시티%20프로젝트/packages/shared/src/stats.ts:1)

건물별 정수 인구는 전체 목표 인구를 먼저 반올림한 뒤 최대 나머지법으로 배분한다. 나머지 동률은 building ID로 정한다. 일자리 배정은 남은 정원에 비례하여 시드 추첨하고, 빈 일자리가 없으면 미취업 상태로 남긴다.

현재 `public`은 학교와 관공서를 구별하지 못한다. 학교 통행을 구현하려면 `activityRole: 'school'` 같은 추가 태그와 별도 학생 정원이 필요하다. 공공 연면적을 전부 학교 정원으로 해석하지 않는다.

**개인 상태 머신**

```text
AtHome
 → LeavingBuilding
 → Walking / WaitingBus / RidingBus / Driving
 → EnteringBuilding
 → AtWork / AtSchool / AtShop
 → 다음 활동
```

하나의 `personId`가 전 과정을 유지한다. 자동차·버스 승객으로 전환될 때 실외 보행 표현만 종료하고 시민 자체는 삭제하지 않는다.

초기 일정 제안:

- 출근·등교 출발: 07:00~09:00 분산.
- 근무 8시간, 수업 6시간을 초기 체류시간으로 사용.
- 귀가 전 상점 방문 확률 30%, 체류 15~45분.
- 도착이 늦으면 이후 일정은 실제 도착시각을 기준으로 조정한다.
- 경로 없음·차량 생성 공간 없음·보행자 상한 도달은 대기 또는 실패 통계로 처리한다.

이 수치는 출퇴근 패턴을 보이게 하는 게임용 초깃값이다. 실제 한국 시간사용·통행조사 기반 보정은 후속 과제다.

**하루 시계와 가속**

물리시간·활동시간·현실시간을 구분한다.

```text
trafficSeconds = tick / 20
calendarSeconds = dayStart + trafficSeconds × calendarScale
```

권장 기본 `calendarScale=1`이다. 현재 워커의 1·2·4배속처럼 여러 고정 스텝을 실행하면 차량·보행·신호·활동을 함께 가속할 수 있다.

`calendarScale=60`으로 낮밤만 빠르게 돌리면 10분 실제 보행이 달력상 10시간을 소비한다. 압축 하루가 필요하면 이를 별도 게임 모드로 명시하고, 통행시간 통계와 체류시간도 그 시간 체계에 맞춰 정의해야 한다. `dt`를 키워 가속하지 않는다.

**거리 기반 수단 선택**

직선거리는 후보 축소에만 쓰고 최종 판단은 도달 가능한 네트워크 경로로 한다.

```text
보행 경로 ≤ 600m:
    도보 우선

600~1,500m:
    도보와 버스의 예상시간 비교

그 이상:
    가능한 버스와 자동차 비교
```

```text
Twalk = 보행거리 / 개인속도 + 예상 횡단대기

Tbus = 접근보행 + 예상 대기 + 버스 주행
       + 하차 후 보행 + 환승 페널티

Tcar = 출발 접근 + 차량 주행 + 도착 접근 + 주차 대체 페널티
```

MVP는 직통 버스만 지원하고, 출발·도착 정류장은 보행 경로 300m 이내 후보로 제한한다. 자동차 보유 여부는 시민별 시드로 한 번 결정한다. 600m·1,500m·300m는 보정 전 제안값이다.

차량은 `personId/tripId`와 연결한다. 출입구에서 승차 접속점까지 걷고, 차량 도착 뒤 마지막 보행 구간을 이어야 사용자가 요구한 실제 이동이 보인다.

**현재 확률 수요와의 중복 방지:** 시민 통행을 도입하면 기존 주거↔비주거 차량 자동 생성은 끄거나 별도 배경 교통으로 분리한다. 같은 통행을 시민 일정과 기존 수요가 각각 생성하면 교통량이 이중 계산된다.

**버스 최소 연동**

- 정류장 대기열: `(arrivalTick, personId)`순.
- 버스별 승객 목록·정원 관리. 초기 정원 40명은 제안값.
- 도착 시 하차 우선, 이후 빈자리만큼 승차.
- 탑승 조건은 노선 ID뿐 아니라 **노선 내 정류장 순서와 목적 정류장**으로 확인.
- 초기 정차시간: `max(기존 10초, 하차 1초/인 + 승차 1.5초/인)`.
- 출발까지 추가 탑승을 허용하면 최대 정차시간을 두고, 마감 후 승객은 다음 버스를 기다린다.
- 차량·노선 삭제 시 승객을 조용히 삭제하지 않는다. 재계획 또는 이동 중단 사유를 집계한다.

**집 안 활동의 저비용 표현**

실내 경로 탐색 없이도 다음을 표현할 수 있다.

- 건물별 현재 재실 인원과 활동 상태를 집계.
- 낮밤·재실 비율에 따른 창문 점등.
- 출입구 앞 1~2m에서 약 1초의 출입 동작.
- 가까운 카메라에서만 문·사람 애니메이션 표시.

이는 **실내 활동의 시각적 요약**이다. 실제 방 안 이동을 구현한 것으로 설명해서는 안 된다.

### 5. 횡단보도: 신호·양보·예약의 통합

**시설과 신호 상태를 분리한다.**

```text
Crossing geometry:
    대기 지점, 횡단 경로, 폭, 충돌 구역, 출구 대기 공간

Pedestrian signal:
    WALK → CLEARANCE(녹색 점멸) → RED
```

- `WALK`: 신규 진입 허용.
- `CLEARANCE`: 신규 진입 금지, 횡단 중인 사람은 계속 이동.
- `RED`: 신규 진입 금지. 잔류자가 있으면 충돌 차량은 계속 대기.

**보행 신호 시간**

제안하는 기본식:

\[
T_{\rm walk}=7s,\quad
T_{\rm clearance}=\left\lceil L/v_{\rm design}\right\rceil,\quad
v_{\rm design}=1.0m/s
\]

틱으로 변환할 때는 안전 구간을 `ceil(seconds × tickRate)`로 올린다.

예를 들어 `L=14m`면 WALK 7초+클리어런스 14초=총 21초다. 기존 기본 차량 녹색 20초에 그대로 넣을 수 없으므로 해당 위상을 연장하거나 별도 보행 위상을 배정해야 한다.

국내 연구 원문은 경찰청 매뉴얼을 인용해 초기 진입 7초, 일반 설계속도 1.0m/s, 당시 교통약자 구역 0.8m/s를 설명한다. **이 연구의 기준연도와 현재 편람을 구분해야 하며, 최신 보호구역 기준은 이번 조사에서 원문 대조하지 못했다.** [국내 보행 신호 연구](https://journal.kits.or.kr/journal/article.php?code=75330&keyword=%EB%B3%B4%EB%8F%84&m=1)

개인속도 0.8m/s인 사람이 마지막 WALK에 진입하면 1.0m/s 설계시간을 넘을 수 있다. 신호시간만 믿고 차량을 풀지 말고 실제 점유가 끝날 때까지 보호한다.

**차량 위상과 동시 진행**

MVP는 보행 전용 위상을 기본으로 제공하고, 검증된 교차로에는 동시 진행을 허용한다.

1. 횡단보도와 차량 **각 이동 경로**의 충돌 관계를 계산한다.
2. 비충돌 직진 이동은 보행과 동시 허용한다.
3. 충돌 우회전·좌회전은 보행자에게 양보한다.
4. 보호 회전 위상은 충돌 횡단보도의 신규 진입을 금지한다.

현재 `laneGreen`만으로는 같은 진입 차선의 직진과 우회전을 따로 제어할 수 없다. `movementPermission(connectorId)`를 추가하거나 `connectorPermission[]`으로 확장해야 한다.

**한국 우회전 규칙**

- **2022년 7월 12일:** 횡단 중인 사람뿐 아니라 횡단하려는 사람에 대해서도 횡단보도 앞 일시정지 의무가 확대됐다. 어린이보호구역의 무신호 횡단보도는 보행자 유무와 관계없이 정지한다. [경찰청 발표](https://m.korea.kr/news/policyNewsView.do?newsId=148903220)
- **2023년 1월 22일:** 전방 차량 적색신호에서 우회전할 때 정지의무가 명확해졌고, 우회전 전용 신호등을 도입했다. [정부 교통제도 안내](https://www.korea.kr/news/policyFocusView.do?newsId=148911493&pkgId=49500788)

따라서 “2022년부터 모든 우회전은 항상 정지”로 모델링하면 부정확하다.

시뮬레이션에서는 적법한 횡단 대기 상태를 `intentToCross`로 표현한다. 적색 보행신호에서 다음 WALK를 기다리는 사람과, 현재 진입이 가능한 횡단 대기자를 구분한다. 법적 횡단 의사 판정을 거리 반경 하나로 대체하지 않는다.

정지 판정의 제안값은 정지선 0.5m 이내·속도 0.1m/s 미만·연속 1초다. **1초는 법정 정지시간이 아니라 시뮬레이션 판정값**이다.

**공유 충돌 구역 예약**

횡단보도를 차량 `Connector` 배열에 직접 넣기보다 별도 `ConflictZone`을 둔다.

```ts
interface ConflictZone {
  id: string;
  vehiclePassages: {
    edge: number;
    enterS: number;
    exitS: number;
  }[];
  pedestrianCrossings: string[];
}
```

컴파일 시 차량 차폭으로 확장한 주행 영역과 보행 통로의 교차를 계산한다. 기존 차량끼리 쓰는 2.5m 중심선 임계값을 모든 보행 충돌에 그대로 적용하지 않는다.

권장 MVP 예약:

- 교차로 차량: 기존 커넥터 허가 시 해당 이동의 횡단 충돌 구역도 함께 검사·예약.
- 구간 중간 차량: 내부 정지선을 넘기 전에 횡단 충돌 구역 예약.
- 보행자: 횡단에 필요한 **모든 충돌 구역과 건너편 수용 공간을 한 번에 예약**.
- 같은 횡단보도의 보행자끼리는 띠·간격이 맞으면 공유 점유 허용.
- 차량은 후미, 보행자는 몸체가 구역을 완전히 벗어난 뒤 해제.

```text
tryGrant(request):
    if 신호·STOP·양보 조건 불충족:
        reject
    if 필요한 구역 중 비호환 예약 존재:
        reject
    if 출구 수용 공간 부족:
        reject
    원자적으로 모든 구역과 출구 공간 예약
    grant
```

차량이 보행자에게 양보하려고 횡단보도 위나 교차로 안에서 멈추는 것을 막으려면, 진입 전부터 출구 횡단보도까지 통과 가능한지 확인해야 한다.

**구간 중간 횡단보도**

MVP는 기존 차량 차선을 쪼개지 않고 `edgePassages[]`와 내부 정지선으로 처리할 수 있다.

- 횡단보도 양쪽 보도에는 접속 노드 삽입.
- 횡단 경로와 모든 주행 차선의 교차 구간 계산.
- 차량 진행 방향마다 횡단 구역 앞 정지선 생성.
- `computeAccelerations()`가 기존 차선 끝뿐 아니라 경로 앞 내부 정지선도 탐색.
- `integrate()`가 허가 없는 정지선 통과를 hard clamp로 차단.

구간 신호 횡단보도는 가까운 교차로와 무관하게 별도 controller ID를 가진다.

**비신호 횡단보도의 갭 판단**

MVP는 보수적으로 모든 충돌 차선의 안전이 확보된 뒤 진입한다.

\[
T_{\rm cross}=L/v_p+2s,\qquad
TTC_k=d_k/\max(v_k,0.1)
\]

진입 조건:

- 기존 차량 점유·허가가 없고,
- 모든 관련 차선에서 차량이 횡단보도 앞에 정지했거나, 접근 차량의 `TTC > Tcross`이며,
- 진입 예약이 같은 틱의 신규 차량 허가보다 먼저 확정됐을 것.

정지 차량 뒤의 추월 가능 차선도 검사한다. 보행자의 갭 판단은 차량의 양보 의무를 대체하지 않는다.

**교착·기아 방지**

- 부분 예약 후 다른 자원을 기다리는 방식을 금지한다.
- 건너편 수용 공간을 선예약하여 횡단 중 막힘을 줄인다.
- 신호는 최소 보행시간을 보장하고, 보행 잔류 시 충돌 차량만 계속 차단한다.
- 비신호 횡단에서 차량 대기가 길어졌다고 횡단하려는 사람을 무시하고 차량을 강제 통과시키지 않는다.
- 지속 혼잡은 신호 설치 권고와 대기시간 통계로 노출한다.
- 예약 timeout으로 실제 점유를 해제하지 않는다. 진입 전 취소 가능한 예약만 명시적으로 취소한다.
- 사망·삭제·재컴파일 시 예약 정리는 별도 경로로 처리한다.

이 구조는 교차로 내부의 부분 예약 교착을 줄인다. **도시 전체 순환 정체의 해소를 보장하지는 않는다.**

### 6. 교통 정온화·규제

**공통 구조: 경로상 속도 제약과 정지 제약**

```text
속도 제약: 제한속도, 보호구역, 방지턱, 회전
정지 제약: 적색신호, 횡단 양보, STOP, 버스 정류장
```

속도 제약은 제한 시작 위치와 끝 위치, 목표속도를 가진다. 정지 제약은 차량별 해제 상태를 가진다.

**과속방지턱**

초기 통과 목표속도는 20km/h, 조절 범위는 10~30km/h를 제안한다. 국토교통 관련 지침은 보행 안전을 위해 차량속도를 30km/h 이하로 제한할 필요가 있는 구간을 설명한다. 제안한 20km/h가 법정 공통 통과속도라는 뜻은 아니다. [과속방지턱 설치·관리 지침](https://www.codil.or.kr/filebank/moctroadguide/LS/CIKCLS200015/CIKCLS200015.pdf)

```text
dBrake = max(0, (v² - targetSpeed²) / (2 × comfortDecel))
vAllowed(d) = sqrt(targetSpeed² + 2 × comfortDecel × max(0, d))
desiredSpeed = min(기존 제한, 경로 앞 제약들의 vAllowed)
```

필요하면 현재 다음 커넥터 감속과 유사하게 적용한다.

\[
a_{\rm target}=
\frac{v_{\rm target}^{2}-v^{2}}{2\max(d,0.5)}
\]

```text
acc = max(-MAX_DECEL, min(IDM_acc, target_acc))
```

50→20km/h, 편안한 감속 2m/s²이면 약 40.5m가 필요하다. 제어 여유 5m를 더하면 약 46m 전부터 반응해야 한다.

방지턱을 속도 0의 가상 선행차로 두면 차량이 정지한다. 통과속도와 감속 제약으로 처리한다. 차량 후미까지 방지턱 구간을 벗어나기 전에는 급가속을 제한할 수 있다.

**어린이보호구역**

- MVP 제한속도 30km/h=`8.333…m/s`.
- 해당 구역의 무신호 횡단보도는 보행자 유무와 관계없이 STOP.
- 구역 진입 전 감속을 계획한다.
- 시간대별 제한은 후속 필드로 둔다.

법 제12조는 보호구역에서 통행속도를 시속 30km 이내로 제한할 수 있도록 규정한다. 모든 실제 보호구역의 운영을 단일 상수로 완전히 재현하는 것은 아니다. [도로교통법 제12조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1030973065)

**STOP·양보 표지**

| 도구 | 처리 |
|---|---|
| STOP | 정지선에서 정지 완료 후 충돌·진출 공간 검사 |
| 전방향 STOP | 정지 완료 틱→차량 ID순 |
| 양보 | 우선 이동 요청·점유와 상충하면 대기, 안전하면 정지 없이 통과 |
| 비신호 교차로 | 현재 FCFS와 구별하여 접근로별 우선권 추가 |

STOP 완료 상태는 `(vehicleId, controlId, 접근 회차)`에 연결한다. 표지 앞에서 매 틱 재정지하거나, 한 번 정지한 이력이 다음 순환 통과에도 남아서는 안 된다.

**과속 단속 카메라**

MVP는 검지선을 넘는 틱에 속도를 기록하는 센서로 구현한다. 모든 차량이 이미 제한속도를 준수한다면 카메라만 추가해도 교통 흐름은 변하지 않는다.

후속으로 운전자별 준수율을 도입할 때 카메라 인지에 따른 감속을 연결한다. 위반 집계 기준과 법적 단속 허용오차를 임의로 동일시하지 않는다.

**가성비가 좋은 추가 도구**

| 우선순위 | 도구 | 효과와 구현 범위 |
|---|---|---|
| 높음 | 회전 금지·이동별 허가 | 커넥터 허용 여부와 경로 비용에 직접 반영 |
| 높음 | 보행 전용 연결·차량 통과 차단 | 접근성을 개선하면서 우회 교통 관찰 |
| 높음 | 신호 오프셋·위상 편집 | 기존 신호 구조 확장으로 효과 확인 가능 |
| 중간 | 고원식 횡단보도 | 횡단보도와 방지턱 제어 재사용 |
| 중간 | 중앙 보행섬 | 횡단을 두 단계로 분리하되 섬 수용량 필요 |
| 중간 | 버스전용 운영 시간 | 기존 버스전용 차선 구조 활용 |
| 후속 | 연석 확장·도로 폭 축소 | 보행거리·회전속도 개선, 기하 변경 비용 큼 |
| 후속 | 주정차·연석 관리 | 실제 승하차·주차 상태가 생긴 뒤 효과적 |

이는 SmartCity 구현 비용에 대한 권고다. 특정 Cities: Skylines 버전의 기본 제공 기능 목록으로 검증한 표는 아니다.

### 7. CityDoc·Command·런타임·스냅샷 계약

**CityDoc에는 편집 가능한 설계만 저장한다.**

```ts
// 제안 스키마의 개념형
Building.entranceLocal?: Vec2;

BuildingType.activityRole?: 'generic' | 'school';
BuildingType.studentCapacity?: number;

CityDoc.crossings: Record<CrossingId, Crossing>;
CityDoc.crossingOverrides: Record<AutoCrossingId, CrossingOverride>;
CityDoc.trafficDevices: Record<DeviceId, TrafficDevice>;
CityDoc.speedZones: Record<ZoneId, SpeedZone>;

Crossing = {
  id,
  segmentId,
  u,                  // 원본 중심선 호 길이 비율
  width,
  control: 'signal' | 'uncontrolled',
  controllerId?
};

TrafficDevice =
  | { kind: 'hump', segmentId, u, targetSpeed }
  | { kind: 'stop' | 'yield', segmentId, dir, u }
  | { kind: 'camera', segmentId, dir, u };

SpeedZone = {
  id,
  kind: 'school' | 'custom',
  ranges: { segmentId, u0, u1 }[],
  speedLimit
};
```

교차로 제어는 `kind`에 STOP·양보를 계속 추가하기보다 다음을 분리한다.

- 신호 운영 여부.
- 접근로별 우선권.
- 정지 의무.
- 이동별 허용·금지.
- 보행 위상과 보행 시간.

`SignalPhase`는 차량 접근로뿐 아니라 허용 이동과 `crossingIds`를 표현해야 한다. 보행 전용 위상을 위해 차량 접근로가 빈 위상도 허용한다. 현재 `buildSignals()`는 유효 접근로가 없는 위상을 버리므로 이 부분을 변경해야 한다.

**필요 명령**

```text
building.setEntrance
buildingType.upsert           // activityRole·정원 포함
crossing.upsert / remove
crossingOverride.set / reset
trafficDevice.upsert / remove
speedZone.upsert / remove
intersection.set              // 확장 계약
activitySettings.set
```

문서 버전을 올리고 이전 문서는 빈 컬렉션과 기본 설정으로 정규화한다. 모든 변경·정규화·삭제 연쇄 규칙은 `shared`에 둔다.

도로 분할 시 시설 위치를 재매핑해야 한다. 특히 현재 `segment.split.t`는 베지어 매개변수이므로, **시설의 호 길이 비율 `u`와 동일하게 취급하면 안 된다.** 분할 지점의 호 길이를 계산한 뒤 양쪽 새 세그먼트로 배분한다.

시민 위치·승객·예약·일정 진행상태는 CityDoc이 아니라 런타임 상태다. 시뮬레이션 스텝 자체에 문서 Command를 매번 생성하지 않는다. 저장소의 “도시 변경은 Command” 원칙은 편집 상태와 정책 변경에 적용한다.

**보행자 스냅샷**

Float32에 장기 증가 ID를 넣으면 `2²⁴`를 넘은 정수를 정확하게 표현하지 못한다. 새 보행 계약은 정수 ID 배열을 별도로 둔다.

```ts
const PEDESTRIAN_STRIDE = 8;

// x, z, heading, speed, gaitPhase, styleIndex, state, elevation
pedestrians: Float32Array;
pedestrianIds: Uint32Array;
pedestrianCount: number;

pedSignals: Float32Array;
pedSignalCount: number;
snapshotVersion: number;
```

- 5천 명 × 8 × 4B = 160KB/스냅샷.
- ID 20KB를 더하면 약 180KB.
- 20Hz면 보행 데이터 약 3.6MB/s. 배열 전송량 기준이며 처리 비용 측정치는 아니다.
- `SnapshotBuffers`, transfer 목록, 반환 풀을 모두 확장한다.
- sim 내부 배열을 직접 transfer하지 않는다.
- ID가 같은 두 스냅샷 사이에서 보간하고, `graphRevision` 변경 시 보간을 중단한다.
- 버스 탑승자는 보행 인스턴스를 숨기고 하차 시 재표시한다.
- 보행 동작 위상은 누적 보행거리에서 계산하여 정지 중 발만 움직이지 않게 한다.
- 창문용 재실 인원과 출입 이벤트는 건물별 별도 집계로 보낸다.

렌더러는 스냅샷을 읽어 인스턴스·LOD·보간만 처리한다.

### 8. 결정적 갱신 순서와 성능 예산

**권장 틱 순서**

```text
1. 확정 Command 반영, 필요한 그래프 재컴파일·재배치
2. 신호 상태·보행 신규 진입 가능 여부 계산
3. 활동 이벤트·수단 전환·버스 승하차 처리
4. 예산 내 경로 탐색
5. 이전 위치 기준 대기 의사·차량·보행 요청 수집
6. 신호·우선권·충돌·출구 공간을 원자적으로 예약
7. 이전 상태 기준 차량 가속·보행 이동량 계산
8. 차량·보행 위치 적분 및 엣지 전이
9. 후미·몸체 기준 예약 해제, 도착·실패 집계
10. tick 증가
```

차량과 보행자를 각각 다른 순서로 움직인 뒤 충돌을 고치는 방식은 피한다. 둘 다 이동 전 같은 상태와 같은 예약 결과를 사용한다.

**차량 3천 대·보행자 5천 명 목표 예산**

| 구간 | 틱당 제안 예산 |
|---|---:|
| 차량 IDM·적분·차선 목록 | 1.20ms |
| 보행 이동·띠 간격·전이 | 0.60ms |
| 신호·충돌 구역 예약 | 0.40ms |
| 활동 이벤트·버스 승하차 | 0.20ms |
| 경로 탐색 | 0.70ms |
| 스냅샷 생성 환산 | 0.40ms |
| 여유 | 0.50ms |
| 합계 | **4.00ms** |

**이 표는 측정 결과가 아니다.** `step()`과 `snapshot()`은 별도 API이므로 각각 계측하고, 총 CPU 비용도 함께 보고해야 한다.

필수 최적화:

- 보행 상태는 SoA/typed array로 유지하고 틱당 객체 생성을 줄인다.
- 보행 띠·차량 차선별 정렬 목록을 유지한다.
- 횡단보도마다 충돌하는 차량 passage만 사전 인덱싱한다.
- 건물·정류장 접속 검색은 컴파일 때 수행한다.
- 시민 활동은 매 틱 전 인구 순회 대신 정수 틱 이벤트 큐로 처리한다.
- 경로 캐시는 `(graphRevision, mode, origin, destination)`을 기본 키로 둔다.
- 교차로 점유·폐쇄 상태가 캐시 결과를 무효화하는 조건을 명시한다.

현재 기본 `routeBudget=200`은 검색 건수 제한이다. 그래프가 커지면 한 번의 A*도 비쌀 수 있으므로 **틱당 확장 노드 수**를 제한하는 재개 가능한 탐색이 필요하다. 초기 목표를 전체 2천 노드 확장/틱으로 두고 측정 후 조정한다.

`performance.now()`로 0.7ms가 지났을 때 탐색을 중단하면 실행 환경에 따라 시민 이동 결정이 달라진다. sim 내부 예산은 작업 수로 고정하고, 시간 계측은 외부 벤치마크에서 수행한다.

**측정 기준 제안**

- 명시한 장비·브라우저에서 워밍업 후 1만 틱.
- 분산 도시와 단일 혼잡 횡단보도 시나리오를 각각 측정.
- 평균·p95·p99, GC, 경로 대기열, 예약 처리량 기록.
- `<4ms`를 평균으로 볼지 p95로 볼지 먼저 확정. 권장은 p95.
- 도로 대규모 편집 재컴파일는 별도 지표로 보고한다. 현재 구조상 편집이 포함된 모든 틱에 4ms를 보장할 근거는 없다.

### 9. 테스트 불변식과 재현 시나리오

| 입력 → 잘못된 결과 | 필요한 검증 |
|---|---|
| 양방향 보도가 있는 일방통행 도로에서 역방향 보행 → 경로 없음 | 차량 방향과 보행 방향 독립 |
| 건물 가까이에 반대편 보도만 존재 → 차도를 가로질러 직접 출입 | access edge 차도 침범 금지 |
| 14m 횡단·WALK 7초·기존 녹색 20초 → 마지막 진입자가 남았는데 차량 출발 | 최소 보행시간과 실제 점유 확인 |
| 차량·보행자가 같은 틱에 진입 요청 → 둘 다 허가 | 원자적 예약, 비호환 동시 점유 금지 |
| 긴 버스 앞부분만 횡단 구역 이탈 → 보행자가 버스 후미와 충돌 | 차량 후미 기준 해제 |
| 편도 2차선에서 한 차선만 정지 → 다른 차선 차량과 보행자 충돌 | 모든 충돌 차선 검사 |
| 건너편 보도가 가득 참 → 사람이 횡단보도 위에 멈춤 | 출구 공간 선예약 |
| 방지턱을 정지 장애물로 모델링 → 차량 완전 정지 | 목표 통과속도·감속 곡선 검사 |
| 보호구역 경계에서만 속도 제한 → 경계 초과속 진입 | 경로 앞 속도 제약 예측 |
| 무신호 보호구역 횡단보도에 보행자 없음 → 차량 무정지 통과 | 보행자와 무관한 STOP |
| 40명 정원 버스에 41명 대기 → 전원 승차 또는 1명 소실 | 정원·잔여 대기열·인원 보존 |
| 시민 수요와 기존 차량 수요 동시 사용 → 동일 통행 이중 생성 | trip ID 기준 생성 책임 일원화 |
| 도로 분할·삭제 중 시민 이동 → 유령 경로·예약 누수 | 재접속·재계획·중단 사유·예약 정리 |
| 긴 실행에서 Float32 ID 사용 → 두 시민이 같은 ID처럼 보임 | Uint32 ID와 재사용 정책 |
| 같은 seed·doc·명령 틱 재실행 → 스냅샷 바이트 차이 | RNG·동률·정렬·체크포인트 검증 |

추가 핵심 불변식:

```text
동일 충돌 구역의 차량 점유와 보행 점유는 양립하지 않는다.
허가 없는 정지선·횡단보도 진입은 없다.
보행자 몸체는 보행 가능 영역을 벗어나지 않는다.
보행 띠 안 최소 간격과 목적 엣지 수용량을 지킨다.
실내 + 보행 + 대기 + 승차 + 운전 시민 수가 전체 시민 수와 일치한다.
reservation count와 실제 holder 목록이 일치한다.
경로 비용·위치·속도에 NaN/Infinity가 발생하지 않는다.
```

동일 엔진 내 반복 결정성과 브라우저·서버 간 바이트 결정성은 구분해 검증한다. ID 정렬, 명시적 동률, RNG 스트림 분리가 필요하며, 플랫폼 간 부동소수점 차이까지 자동으로 해소되는 것은 아니다.

**구현 순서**

1. 보행 그래프·출입구·도보 왕복과 보행 스냅샷.
2. 보행 전용 신호 위상·공유 예약·구간 중간 횡단보도.
3. 지속 시민 일정·자동차 연결·기존 수요 중복 제거.
4. 실제 버스 승하차.
5. 방지턱·보호구역·STOP·양보.
6. 회전 동시 진행·추월 띠·중앙 보행섬·군중 모델.

각 단계는 해당 안전 불변식과 재현 테스트가 통과한 뒤 통합한다.

## 위험과 미해결 질문

1. **성능 목표의 범위를 확정해야 한다.** 보행자 5천 명이 전체 시민인지 동시 실외 인원인지, 4ms가 평균인지 p95인지에 따라 설계 규모가 달라진다.
2. **압축 하루는 시간 모델 결정이 먼저다.** 낮밤만 빠르게 돌리면 이동시간과 활동시간이 어긋난다. MVP는 같은 시간축과 고정 스텝 배속을 권장한다.
3. **법규 모사 범위를 명시해야 한다.** 이번 확인으로 2022·2023 변경은 구분했으나 최신 신호 편람 전체와 모든 현장 예외를 대조하지 않았다.
4. **기존 차량 위치 의미를 유지해야 한다.** 현재 `s`와 후미 해제 관례에 맞춰 내부 정지선·충돌 passage를 정의하지 않으면 차체가 횡단 구역에 남을 수 있다.
5. **기하 실패를 숨기면 안 된다.** 예각·짧은 도로·급곡선·보도 단절에서 컴파일 실패 시설을 표시하고 시민을 미접속으로 집계해야 한다.
6. **좁은 보도·정류장·보행섬의 수용량이 필요하다.** 단순 측방 오프셋만으로는 합류·대기열·상호 막힘을 해결하지 못한다.
7. **도시 전체 정체는 별도 문제다.** 차량·보행 예약으로 안전을 보장해도 순환 정체가 사라지지는 않는다. 대기시간·실패·제거 통계를 유지해야 한다.
8. **재난 대응의 타당성은 아직 확보되지 않는다.** 제안 MVP는 시민 이동과 시설 반응을 보여주는 기반이다. 대피 행동·밀집 보행 용량·교통약자·실측 수요를 보정해야 재난 결과를 평가할 수 있다.
9. **공개 API 확장은 Lead 결정 사항이다.** `RoadGraph`, `SimSnapshot`, `SnapshotBuffers`, `SignalPhase` 변경은 기존 sim 규칙에 따라 계약 검토와 ADR로 확정해야 한다. 이 보고서는 설계 제안이며 코드 승인이나 실행 검증을 대신하지 않는다.
