## 요약 (5줄 이내)
1. 원인은 "회전이 우클릭 드래그에만 있고 아무 힌트도 없음". 해결은 3겹: (a) 항상 보이는 **뷰 큐브/방향 버튼**(앞·뒤·좌·우·위, 클릭 시 부드럽게 이동), (b) **키보드 회전**(Q/E, 방향키, 숫자패드), (c) **온보딩 힌트**(첫 진입 시 3줄 + `?` 버튼). 힌트 문구의 "우클릭=지우기"는 "회전은 우클릭 드래그, 지우기는 Shift+클릭"으로 정정.
2. 이미지→건물은 **Claude 비전 + 기존 create_building_design(블록)** 이 MVP. 메시 생성 서비스(Meshy/Tripo/Rodin/TRELLIS/Hunyuan3D)는 결과가 "삼각형 메시"라 복셀 스튜디오에서 편집 불가 -> 후속(참고용 레퍼런스/장식 prop)으로만.
3. **Hunyuan3D 2.x 라이선스는 EU·영국·대한민국을 제외**(확인) -> 한국 프로젝트에 사용 불가에 가까움. TRELLIS(MIT)가 오픈모델 중 안전.
4. **Blender는 "개발자 오프라인 도구"로만** 사용(차량/장식 prop을 GLB로 굽기). 서버 런타임 bpy는 도입하지 않음. 에셋은 Kenney/Quaternius CC0 우선.
5. AI 변경 강조는 **카메라 fly-to + 목록의 "이동" + 맥박(emissive) 몇 초 + 미니맵 ping** 조합. 상시 OutlinePass는 비용 대비 비추천.

## 0. 현재 코드 사실 (확인: 저장소 직접 열람)
- `apps/web/src/studio/StudioScene.ts` 165~170행: `left=NONE`(도구용), `right=ROTATE`, `middle=TRUCK`, `wheel=DOLLY`, 터치 `one=TOUCH_ROTATE`.
  - 즉 터치는 이미 한 손가락 회전이 되지만, **한 손가락 터치가 도구 입력과 충돌하는지 별도 확인 필요**(미검증).
- `onKey`(661~701행) 사용 중인 키: `Ctrl/Cmd+Z`, `Ctrl/Cmd+Shift+Z`, `Ctrl/Cmd+Y`, `Escape`, **`1`~`6`(도구)**, `R`(prop 도구에서만), `[` `]`(prop 도구에서만), `F`(frame). `mod || altKey`면 조기 return -> **Alt 조합은 현재 아무 기능도 없음**(Alt+좌클릭 회전을 넣어도 충돌 없음, 단 `onPointerDown`이 `e.altKey`를 보는지는 확인 필요).
- 스튜디오는 keydown을 capture로 가로채고 `stopPropagation` -> 도시 쪽 단축키와는 충돌하지 않지만, 입력창(`isTyping`)에서는 통과.
- `TOOL_INFO.stack.hint`: "...우클릭/Shift+클릭 = 지우기" 이므로 우클릭이 지우기로 읽힘. `camera-controls`는 우클릭 드래그를 회전으로 쓰므로 **클릭(이동 거의 없음)=지우기, 드래그=회전**으로 이미 분기하고 있을 가능성이 큼(press/drag 구조 `drag.kind==='press'`). 이 분기 임계값은 구현 시 확인.
- `F`=frame 이미 존재: "선택/건물에 맞춰 보기"의 뼈대가 있음.

### 1-2. 패턴 정리 (우리에 맞는 것만)
1. **뷰 큐브 / 방향 버튼**: 가장 큰 효과. 최소형은 캔버스 모서리에 `앞 뒤 좌 우 위` 5버튼 + `전체 보기(Home)` + `선택 맞춤(F)`.
2. **스냅 이동은 즉시가 아니라 0.3~0.5초 보간**: `camera-controls`의 `rotateTo(azimuth, polar, true)`가 이미 지원(확인: github.com/yomotsu/camera-controls README). 방위각 0=앞, 90도=왼쪽, -90도=오른쪽, 180도=뒤, 극각 180=위(라이브러리 규약. 우리 모델의 "앞" 정의와 맞는지 확인 필요).
3. **키보드 회전**: Q/E 또는 방향키로 일정 각도(15도, Shift면 90도). Goxel/CS2/Blender 모두 제공.
4. **Alt+좌클릭 드래그=회전**: 우클릭이 없는 트랙패드/펜 대응(Blender Emulate 3 Button). 현재 Alt 조합은 비어 있음.
5. **선택 중심 회전**: `setOrbitPoint`(확인)로 선택된 덩어리 중심에 회전축을 맞춤. 건물 "뒤쪽" 편집 시 화면 밖으로 날아가는 문제 방지.
6. **층 분리 보기**: (a) 현재 층 이하만 표시(이미 `upperHidden` 있음), (b) 위층 반투명 X-ray, (c) 컷어웨이(앞쪽 벽만 숨김). 우선순위는 (b) > (c).
7. **온보딩**: 첫 진입 때 비차단 토스트 3줄 + 상시 `?` 버튼 + 마우스 커서가 캔버스 위일 때 하단 힌트바 갱신. localStorage로 "다시 보지 않기"(try/catch 필수).

### 1-3. 권장 조작 스킴 (마우스 / 트랙패드 / 터치)
| 동작 | 마우스 | 트랙패드(우클릭·휠 약함) | 터치 |
|---|---|---|---|
| 도구 사용 | 좌클릭/드래그(현행) | 좌클릭/드래그(현행) | 한 손가락 탭/드래그 (**회전과 충돌 -> 아래 참고**) |
| 회전 | 우 드래그(현행) | **Alt+좌 드래그**, 또는 두 손가락 클릭 드래그 | 두 손가락 비틀기/기울기 or **회전 모드 토글 버튼** |
| 팬 | 중간 드래그 / **Shift+우 드래그**(추가) | Shift+Alt+드래그 | 두 손가락 이동 |
| 줌 | 휠 | 핀치/두 손가락 스크롤 (`wheel`로 들어옴) | 핀치 |
| 지우기 | Shift+클릭 / 우클릭(이동<임계값) | Shift+클릭 | 지우개 도구 |
| 뷰 스냅 | 큐브/버튼 | 큐브/버튼 | 큐브/버튼 |

- **터치 충돌 해결**: 현재 `touches.one=TOUCH_ROTATE`인데 도구도 한 손가락을 쓴다. 제안: 터치에서 한 손가락=도구(탭/드래그), **두 손가락=회전+줌+팬(`TOUCH_DOLLY_TRUCK` 또는 ROTATE 조합)**, 그리고 화면 구석에 "이동/편집" 토글 버튼. 구체적 ACTION 조합은 camera-controls의 `touches.two` 옵션(TOUCH_DOLLY_ROTATE 등 존재: 확인)으로 가능.
- **키 맵 (기존 키와 비충돌 확인됨)**:
  - `Q` / `E`: 15도 좌/우 회전 (Shift=90도). 사용 중 아님.
  - `←` `→`: 좌/우 회전, `↑` `↓`: 기울기(polar). 사용 중 아님. (건물 선택 중 화살표를 다른 용도로 쓸 계획이 있으면 재검토)
  - `Numpad1/3/7` = 앞/오른쪽/위, `Ctrl+Numpad1/3` = 뒤/왼쪽 (Blender 관례). `e.code`로 판별해야 상단 숫자열 `1~6`(도구)과 구분됨.
  - 숫자패드 없는 노트북용: `V` = 앞->오른쪽->뒤->왼쪽->위 순환. 사용 중 아님.
  - `Home`: 전체 보기(초기 시점), `F`: 선택/건물 맞춤(현행 유지).
  - `T`: 위층 투명(X-ray) 토글 등은 후속. (`T`,`V`,`Q`,`E`,`X`,`C` 등 문자키는 아직 비어 있음. 단 다른 도구 단축키를 추가할 계획과 겹치지 않게 키 표를 `TOOL_INFO` 옆에 한 곳으로 모을 것.)
  - IME(한글) 입력 상태에서는 `e.key`가 한글로 나오므로 문자키 단축키는 `e.code`('KeyQ' 등)로 판별 권장(기존 코드는 `e.key.toLowerCase()` 사용 -> 한글 IME 켜진 상태에서 `F`가 안 먹을 수 있음. **미검증, 확인 필요**).
- **힌트 문구 정정 예**: "회전: 우클릭 드래그(또는 Alt+드래그, Q/E) · 이동: 휠 클릭 드래그 · 확대: 휠 · 지우기: Shift+클릭 · 뒤쪽 보기: 오른쪽 위 큐브의 '뒤'". 현행 stack 힌트의 "우클릭=지우기"는 오해 유발.
- **패널이 캔버스를 가림**: 패널 접기 버튼/`Tab`로 패널 숨기기(UI-less 모드). 큐브는 패널과 겹치지 않는 위치에 배치. 접힌 상태에서 `fitToBox`의 `paddingRight/Left` 옵션(확인)으로 패널 폭만큼 여백을 주면 건물이 패널에 가리지 않음.

### 1-4. 구현 비용 추정
- 뷰 버튼 5개+Home+Fit: 반나절 (React 컴포넌트 + `controls.rotateTo`/`fitToBox` 호출).
- 키보드 회전, Alt 드래그, 힌트 정정: 2~3시간.
- 진짜 3D 뷰 큐브(작은 별도 three 씬): 반일~1일. 버튼 5개로 충분하면 후순위.
- 터치 재매핑: 반일 + 실기기 테스트.

## 3. 이미지(사진/도면) -> 3D 건물
### 3-1. Claude 비전 한도 (확인: https://platform.claude.com/docs/en/build-with-claude/vision)
- 입력 방식 3가지: **base64 / URL / Files API `file_id`**. (Bedrock·Google 관리형은 base64만.)
- 형식: **JPEG, PNG, GIF, WebP**. GIF는 첫 프레임만.
- 크기: API **10 MB(base64 기준)/장**, claude.ai 10 MB, Bedrock 5 MB. 최대 해상도 **8000x8000 px**. 요청 전체 크기 32 MB 제한.
- 개수: API 요청당 **100장(200k 컨텍스트 모델) / 600장(그 외)**, claude.ai는 20장. **20장 초과 시 장당 2000 px 이하**로 제한 강화.
- 비용: 이미지 토큰 = ceil(가로/28) x ceil(세로/28). 모델 등급별 긴 변 한도: **고해상도 등급(Claude 4.7 이후) 2,576 px / 최대 4,784 토큰, 표준 1,568 px / 1,568 토큰**. 예: 1000x1000은 1,296 토큰. 문서 예시 가격(Opus 5.5 $4/MTok 기준 1000x1000 약 $5.18/천 장)은 문서 작성 시점 값이므로 구현 전 재확인.
- 모델이 인정하는 한계(확인): **공간 추론/좌표는 근사치**, 작은 객체 **카운팅은 부정확**할 수 있음, 200 px 미만·회전·저화질 이미지는 환각 가능. 이미지 메타데이터(EXIF) 미전달. 업로드 이미지는 요청 후 삭제, 학습에 사용 안 됨(문서 기술).
- 권장 입력: 이미지를 텍스트보다 **앞에** 배치. 여러 장이면 "Image 1:" 라벨. 우리 앱은 클라이언트에서 긴 변 1568~2000 px로 리사이즈 + JPEG 품질 85 이상으로 올리는 것이 비용/지연 면에서 합리적.
- 우리 서버(`apps/server/src/ai/*.ts`)에는 현재 이미지 입력 경로가 **없다**(grep 결과 image/vision 언급 없음): 업로드 UI + multipart 또는 base64 JSON + 서버 크기 제한이 신규 개발 필요.

핵심 판단: 우리 스튜디오 데이터는 "2 m 격자 복셀 + 용도/재질"이다. 메시 생성기는 **외형은 닮지만 층/방/용도 정보가 없고 편집 불가**한 덩어리를 준다. 사용자 요구("같은 건물을 3D로")를 지키면서 이후에 계속 편집하려면 (a)가 유일하게 맞다. (b)는 "외관 레퍼런스 장식 prop(GLB로 올려놓고 보기만)" 같은 후속 기능으로만 의미가 있다.

### 3-3. 권장안 (MVP -> 후속)
**MVP (a)**: 
1. 업로드 UI(사진/도면 1~4장, JPEG/PNG/WebP, 클라이언트에서 긴 변 ~1568~2000 px 리사이즈).
2. 서버: Messages API image 블록 + 기존 도구. 프롬프트를 **2단계**로: (i) 분석 단계 — 층수, 층고 비율, 전체 가로x세로 칸 수(2 m 격자 환산), 지붕 형태, 창/출입구 위치, 재질/색을 먼저 **텍스트 JSON으로 선언** (ii) 생성 단계 — 그 JSON대로 `create_building_design` 호출. 분석 단계를 분리하면 사용자가 "층수 4가 맞나요?" 확인/수정 가능하고 평가도 쉽다.
3. 사용자가 치수를 아는 경우 입력 필드(가로 m, 층수) 제공 -> 모델의 "근사 공간 추론" 한계(확인된 한계)를 보완.
4. 생성 후 같은 이미지를 **두 번째 호출로 되먹임**(원본 + 현재 모델의 4방향 스크린샷) -> "다른 점 3가지와 수정" 1~2회 반복(자기 수정 루프). 스튜디오에서 4방향 렌더를 얻으려면 1절의 뷰 스냅 API를 재사용 가능.
5. 모호할 때 도면(평면도)이면 평면도 모드, 사진이면 정면 파사드 모드로 프롬프트 분기.

**후속**: 정면/측면 여러 장 입력, 건물 외 소품은 CC0 GLB 라이브러리에서 매칭, (선택) 자체 GPU가 생기면 TRELLIS로 외형 레퍼런스 생성.

### 3-4. 충실도 평가 방법
- **오프라인 벤치**: 사진 10~20장(저층 주택, 상가, 아파트, 도면 3종 포함) + 사람이 만든 정답 복셀 모델. 지표: 층수 일치, 가로/세로 칸 오차(+-1칸), 지붕 형태 일치, 창/문 개수·위치 근사, 주 색상 CIELAB 거리, 복셀 3D IoU(정답 대비).
- **시각 비교**: 모델 4방향 렌더 vs 원본을 사람 3명이 1~5점(블라인드). 합격선(예: 평균 3.5 이상)을 사전에 정함.
- **자동 LLM 심사는 보조만**: 같은 모델이 만들고 같은 모델이 채점하면 자기 승인 문제. 다른 모델(예: Argon)이나 사람 점수와 상관을 먼저 확인.
- 비용/지연 기록: 호출당 입력 토큰, 출력 토큰, 총 시간, 사용자 수정 횟수.

## 4. Blender
### 4-1. 확인된 사실
- Blender 공식: "What you create with Blender is your sole property" — GPL은 Blender 소스와 **공개하는 Python 애드온/스크립트**에 적용되고, **산출물(작품/에셋)에는 적용되지 않음**(확인: blender.org/about/license).
- Kenney 에셋은 전부 CC0(퍼블릭 도메인), 상업 이용·무표기 가능(확인: kenney.nl/support). 차량/건물 키트 존재 여부는 에셋 목록에서 직접 확인 필요(미검증).
- Quaternius 모델은 전부 CC0(확인: quaternius.com/faq).
- three.js `GLTFLoader`는 Draco(`DRACOLoader`), KTX2(`KTX2Loader`), meshopt(`MeshoptDecoder`) 확장을 지원. 디코더 파일을 정적 경로로 서빙해야 하고 `file://`에서는 동작 안 함(three.js 문서 + 일반 사용법, 세부는 부분 미검증: threejs.org/docs).

### 4-2. 에셋 파이프라인 제안 (오프라인)
1. 소스: Kenney/Quaternius CC0 GLB 우선 사용 -> Blender에서 단위/원점/방향 정리(바닥 중심 원점, +Y 위, 1 단위 = 1 m), 폴리곤 감소.
2. 내보내기: **glTF 2.0 binary (.glb)**, 머티리얼은 PBR 최소화(또는 flat color 팔레트 텍스처 1장으로 통합해 드로우콜 감소).
3. 최적화: `gltf-transform`(오픈소스 CLI, **미검증: 라이선스 확인 필요**)로 meshopt 또는 Draco 압축. 작은 prop은 압축 이득이 작으니 크기/디코더 로딩 비용을 비교 후 결정.
4. 런타임: `GLTFLoader` 1회 로드 -> 지오메트리/머티리얼 캐시 -> 차량/장식은 **`InstancedMesh`** 로 배치(수백 대도 1 드로우콜). 개별 색은 `setColorAt`.
5. 출처 관리: `public/assets/LICENSES.md`에 팩 이름, URL, 라이선스(CC0), 수정 여부를 한 줄씩 기록.

### 4-3. 서버 런타임 headless bpy가 필요한가?
- 필요 없음. 이유: (1) 사용자가 업로드한 모델을 변환하는 요구가 지금 없음, (2) bpy/Blender는 수백 MB, 콜드 스타트·동시성 관리·보안(임의 파일 처리) 부담, (3) 프로젝트가 Node/TypeScript 중심, (4) 복셀 파이프라인은 Blender가 관여하지 않음. 또한 서버에서 Blender를 **네트워크 서비스로 제공**하는 것은 Blender 자체 GPL 의무(배포 시 소스 제공)에 관한 검토 항목이 생길 수 있으나, 내부 사용은 일반적으로 문제 아님(법률 해석 **미검증**).
- **결론**: "Blender 사용 = 예, 개발 PC에서 에셋 정리/내보내기용. 런타임 = 아니오." GPL 코드(Goxel 등 포함)는 복사하지 않음. 에셋 소스는 산출물만 저장소에 커밋(.blend 원본 보관은 선택).
- 사람 시간 투자가 큰 질문: **정말 차량/prop 메시가 필요한가?** 현재 시스템이 복셀·절차형이라면 차량도 복셀 prop으로 통일하는 편이 스타일 일관성에 유리. 메시 도입은 "CC0 차량 몇 종" 수준에서 시작 권장.

## 5. AI가 만들거나 바꾼 오브젝트 강조 (three.js)
| 방식 | 체감 효과 | 성능 | 인스턴스드 메시에서 | 권장 |
|---|---|---|---|---|
| 맥박 emissive | 중 | 매우 낮음(유니폼/색 변경) | `InstancedMesh`는 인스턴스별 emissive 불가 -> 인스턴스 색(`setColorAt`)을 시간에 따라 밝게 섞거나, 강조 대상만 별도 메시/그룹으로 분리 | **필수(2~4초 후 소멸)** |
| OutlinePass (postprocessing) | 높음 | 풀스크린 패스 추가 -> 저사양/고해상도에서 비쌈. 선택된 오브젝트가 많으면 더 비쌈 | 인스턴스 일부만 선택하기 어려움(선택 레이어/복제 메시 필요) | 상시 사용 비추천. **목록에서 "이동" 클릭한 한 건만** 쓰는 용도로는 가능 |
| 빛기둥/비콘 | 높음(멀리서도 보임) | 낮음(스프라이트/가산 블렌딩 실린더 몇 개) | 영향 없음(별도 메시) | **권장**, 건물 위로 세운 반투명 원기둥, 거리/카메라 구분 |
| 미니맵 ping | 높음 | 매우 낮음 | 영향 없음 | **권장**(2D 오버레이 확장 링 애니메이션) |
| 카메라 fly-to | 높음 | 낮음 | 영향 없음 | **권장**: 스튜디오와 같은 `camera-controls`의 `fitToBox`/`setLookAt(..., true)` 재사용 |
| "변경 목록 + 이동" | 높음 | 없음 | 영향 없음 | **필수**: 채팅 응답/패널에 `[건물 A 생성됨] [이동]` 항목. 여러 개 변경 시 이전/다음 |

- 성능 원칙: 강조 상태는 변경 이벤트 후 N초 동안만 프레임 업데이트. 상시 애니메이션 요소를 두지 않아 대기 시 GPU 부하를 만들지 않는다. `renderer.info`로 드로우콜/삼각형 수 측정해서 임계치 관리.
- 스튜디오(복셀)와 도시(다수 건물)는 별개 장면이므로, 도시 장면에서는 "변경된 건물 id 집합"만 관리하면 되고 스튜디오 내부에서는 "변경된 셀 집합"을 같은 방식(맥박 색)으로 처리 가능.
- three.js `OutlinePass`의 세부 API와 `InstancedMesh.setColorAt` 동작은 three.js 공식 문서/예제를 구현 시점 버전으로 직접 확인할 것(이번 조사에서는 해당 페이지를 직접 읽지 못함 -> **미검증**).

## 권장안 요약 (MVP / 후속)
**MVP (1~2일)**
1. 힌트 문구 정정 + 첫 진입 온보딩 + `?` 버튼.
2. 뷰 스냅 버튼(앞/뒤/좌/우/위/Home/맞춤) — `rotateTo`, `fitToBox`.
3. 키 `Q/E`, 방향키, `V`, Numpad, Alt+좌 드래그 회전, Shift+우 드래그 팬.
4. 패널 접기/`Tab`, 패널 여백을 반영한 맞춤.
5. Undo/Redo 버튼 노출.
6. 변경 목록 + "이동"(fly-to) + 맥박 강조.

**후속**
7. 미러, 영역/층 복사, X-ray 위층.
8. 이미지->건물(Claude 비전 + 2단계 + 자기수정 루프) + 벤치마크.
9. 터치 재매핑(두 손가락 회전) 실기기 검증.
10. CC0 GLB prop 파이프라인(Blender는 개발 PC 한정).

## 위험과 미해결 질문
1. 우클릭 "클릭=지우기 vs 드래그=회전" 분기 임계값이 실제로 어떻게 구현돼 있는지 `onPointerDown/Up` 확인 필요(트랙패드에서 의도치 않은 지우기 위험).
2. 터치: 한 손가락이 도구와 회전에 동시에 할당되어 있을 가능성. 실기기 테스트 필요.
3. 한글 IME 상태에서 `e.key` 기반 단축키 동작 여부(`F`, 신규 키). `e.code` 전환 여부 결정 필요.
4. 이미지->건물의 실제 충실도는 벤치마크 전까지 **알 수 없음**. 모델이 공간·카운팅에 약하다는 공식 한계가 있으므로 "사용자 확인 단계"를 UX에 반드시 포함.
5. 이미지 업로드는 개인정보/저작권(타인 건물 사진, 도면) 이슈 가능. 서버 저장 여부 정책 필요(Anthropic은 요청 후 삭제하나 우리 서버는 별도).
6. Meshy/Tripo/Rodin의 형식·가격·상업 이용 조건은 **미검증**. 후속 도입 전 직접 확인.
7. Hunyuan3D는 한국 제외 조항 때문에 법무 확인 전 사용 금지.
