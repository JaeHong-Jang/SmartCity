## 요약 (5줄 이내)
1. **도로 모서리 원인은 "차수 2 노드의 접합 폴리곤이 4개 모서리를 각도순으로 이은 쐐기"** (`compile.ts` junctionPolygon, setback = 반폭+1). 시뮬 차선은 이미 3차 베지어 커넥터(핸들 0.4d)로 이어져 거의 원호에 가깝지만 화면 폴리곤이 그것과 안 맞는다.
2. **권장: "그릴 때 문서에 구워 넣는 필렛"**. 꺾임 꼭짓점 V에서 거리 T=R·tan(δ/2)만큼 물러난 두 점 사이를 **제어점=V인 2차 베지어 segment 1개**로 잇는다(기존 `control` 필드만 사용, 스키마·시뮬·골든 해시 변경 없음). 기존 꺾임은 "모서리 둥글게" 명령(배치 커맨드)으로 사용자가 선택 변환. 렌더 전용 스무딩은 시뮬 차선과 어긋나므로 **차수 2에는 비추천**, 차수 3+ 교차로 연석 코너만 렌더 전용으로 둥글게(시뮬 무관).
3. **그리기 UX**: 직선 기본 + 꺾임 자동 필렛(미리보기 실시간) / 곡선 2클릭(기존 도로 끝에서 시작하면 접선 연속) / 자유곡선(마우스 경로 → RDP → 중점 2차 B-스플라인으로 segment화). 격자 스냅은 "소프트(자석) 스냅 + 15° 각도 스냅 + 가이드선"으로 교체, Shift=해제.
4. **건물 배치**: 고스트를 임계감쇠 스프링으로 보간(위치·각도, 최단 각도), 도로 선택 히스테리시스, 도로 따라 스냅은 자석 구간으로, 곡선 도로에선 폭만큼의 할선(secant)으로 정렬. 회전은 기존 `, .`(15°)·`[ ]`·Alt(1°) 유지 + **R 누른 채 마우스 이동 = 연속 회전**.
5. **곡면 건물 권장: `BuildingPart.round?`(모서리 반경, m) 하나만 추가** — 직교 footprint/사각형 + 반경으로 `partOutline()`이 둥근 다각형(고정 sin/cos 표)을 돌려주면 충돌·면적·지오메트리·고스트가 자동으로 따라온다. 스튜디오는 VoxelStyle에 `round`(0/1/2셀), AI 툴은 블록별 `corner_radius`. 지붕 dome/cone은 후속(계약 변경). 일반 곡선 다각형(자유 곡면)은 그다음.

### A-2. 수학
**원호 필렛.** 두 직선 도로가 꼭짓점 V에서 만나고 진행 방향 편향각이 δ(직진=0, U턴=180°)일 때, 반경 R 원호가 접하려면 V에서 각 직선을 따라 **T = R·tan(δ/2)** 만큼 물러난 점에서 접한다(기하학 표준식, 유도). 호 길이 = R·δ.

**3차 베지어로 원호 근사.** 중심각 θ인 원호는 끝점 접선 방향으로 제어점을 `R·k`(k = 4/3·tan(θ/4))에 두면 된다. 1/4원 k≈0.55228, 최대 반경 오차 약 0.00027R (확인(웹): pomax.github.io/bezierinfo "Circular arcs and cubic Béziers"). 이 프로젝트의 `makeConnector` 핸들 0.4·d를 이 식과 비교하면(유도, 직접 계산) 현 커넥터는 이미 원호에 가깝다.

| 편향 δ | 이상적 핸들/현 d | 현 핸들 0.4 | 해석 |
|---|---|---|---|
| 30° | 0.339 | 0.4 | 약간 부풀지만 시각 차이 작음 |
| 60° | 0.373 | 0.4 | 거의 일치 |
| 90° | 0.390 | 0.4 | 사실상 원호 |
| 120° | 0.403 | 0.4 | 일치 |

→ **"시뮬 차선 커넥터가 이미 원호형인데 화면 폴리곤만 쐐기"** 이므로, 시각을 시뮬 쪽에 맞추는 것이 가장 싸고 안전하다.

**2차 베지어 필렛(우리 segment 형식).** 접점 P0 = V − T·u0, P2 = V + T·u1, 제어점 = V 로 두면 접선 연속(G1)이고 한 segment로 표현된다. 대칭일 때 정점(apex) 곡률반경은 `R_apex = T·cos²(δ/2)/sin(δ/2) = R_arc·cos(δ/2)` (유도, 직접 계산). 즉 포물선형이 원호보다 중앙이 조금 더 급하다(δ=90°에서 0.71R, δ=60°에서 0.87R). 따라서 **설계 반경은 R_arc 기준으로 잡고 안쪽 여유는 R_apex로 검증**한다. 2차 베지어는 정확한 원이 아니므로 "원호처럼 보이는 곡선"이지 수학적 원이 아님(pomax: 2차는 3차보다 오차가 약 두 자릿수 큼, 확인(웹)).

**최소 반경 vs 폭 (안쪽 가장자리 자기교차 방지).** 중심선 곡률반경 ρ, 중심선에서 바깥 가장자리까지 반폭 w_total(=roadHalfWidth)일 때 안쪽 오프셋 반경은 ρ − w_total. 이것이 0 이하면 오프셋이 뒤집혀 자기교차(스크린샷의 안쪽 겹침). 따라서
- 시각/보도 기준: **R_min = w_total + 여유(권장 3~4 m)**. 8차선(w_total 16.5) → R_min ≈ 20 m, 2차선(w_total 3.5+2.5=6.0 → 계산: 차도 7 / 2 + 2.5 = 6.0) → ≈ 9~10 m.
- 속도 기준: 우리 커넥터는 `v = √(2.5·반경)` 이므로 설계 속도 v에 대해 `R_speed = v²/2.5`. 50 km/h(13.9 m/s) → 77 m, 70 km/h → 151 m. 도시 맵(300 m급 소형 도시 포함)에서는 과대하므로 **R = clamp(R_speed, R_min, R_cap)**, R_cap은 도로 타입별 상한(예: 소로 25 m, 대로 60 m) 같은 **튜닝 파라미터(결정 필요)**.
- 길이 기준: T = R·tan(δ/2) ≤ 인접 segment 가용 길이(양쪽이 서로 T를 쓰는 짧은 도로 포함). 가용 길이를 넘으면 R을 줄이고, R_min에서도 안 되면 "필렛 불가"로 꺾임 유지. δ가 150°를 넘으면 tan이 폭주하므로 필렛 제외(헤어핀은 사용자가 곡선 도구로).
- `minSegmentLength=8`: 호 길이 R·δ ≥ 8, 남는 직선 조각도 ≥ 8 이어야 한다(planRoad 오류 규칙과 일치).
- 연속 접선에서의 구현 상세: 한 변이 이미 베지어이면 그 끝의 접선과 호 길이 기준 접점으로 일반화(근사). MVP는 직선-직선 꺾임만.

**다차선에서 차선별 반경.** 차선 i는 중심선 오프셋 o_i만큼 이동한 곡선이라 반경이 R ± o_i. 바깥 차선이 길고 안쪽이 짧다. `offsetPolyline`은 점별 접선 법선으로 이동하므로 2 m 샘플링 곡선에서 정상 작동한다(안쪽 R−o>0 이어야 함 → R_min 규칙이 보장).

### A-3. 방식 비교

|---|---|---|---|
| **A1. 그릴 때 문서에 굽기** (직선 + 2차 베지어 호 + 직선) | 문서=진실 유지, 시뮬 차선은 평범한 segment라 **가시 도로와 100% 일치**, 새 필드 없음, 서버 검증 그대로, 되돌리기 1스텝(batch) | 꺾임 1개당 segment 3개(노드 2개 증가), 이후 꼭짓점을 끌면 호가 따라가지 않음(선택/삭제 도구와의 UX 보완 필요) | **기존 문서/골든 불변** (명시적 커맨드만 사용). 기존 꺾임은 "모서리 둥글게" 사용자 액션으로만 변환 |
| A2. 컴파일 시 파생 (`compileNetwork`가 차수 2 노드에서 setback=T로 자르고 호 커넥터 생성) | 문서 불변, 꺾임을 나중에 움직여도 자동 | `compileNetwork` + 렌더 + 접합 폴리곤 + 횡단보도/정지선 규칙 전반 수정, 반경 설정을 어디 저장할지(노드 필드? 전역?) 필요, **차수 2 컴파일이 있는 모든 골든 문서 해시 변경 가능** | 골든 재기록 + 의회 승인 필요. 옵트인 필드(`node.round?`)로 구버전 보존 가능하지만 커맨드·검증·AI·마이그레이션 계약 변경(L) |
| A3. 렌더 전용 스무딩 (접합 폴리곤만 둥글게) | 가장 작음(S), 해시 무관 | **시뮬 차선은 setback 17.5 m 간격을 커넥터로 건너뛰므로 화면 아스팔트 밖으로 벗어날 수 있음**, 차선 마킹·보도는 setback에서 끊김 → 근본 해결 아님 | 해시 불변 |
| A4. 렌더 전용 + 접합 폴리곤을 시뮬 커넥터 곡선으로 채우기 | 시각-시뮬 일치(커넥터 외곽선 오프셋으로 폴리곤 생성), 해시 불변 | setback이 크면(8차선) 직선 구간 17.5 m가 비어 있어 마킹/보도 단절이 남음, 구현 복잡 | 해시 불변 |

**권장: A1을 본체로, 차수 3+ 교차로 코너만 A3 방식(렌더 전용)으로 개선.**
- 이유: 우리 아키텍처에서 "시뮬은 segment에서 차선을 컴파일하고 렌더도 같은 결과를 쓴다"는 불변식을 깨지 않는 유일한 저비용 경로가 "곡선도 segment"로 표현하는 것이다. 이미 `control` 필드와 `planRoad`의 분할 로직(`splitQuadBezier`)이 있다.
- **차수 3+ 교차로(렌더 전용)**: 인접한 두 다리의 가장자리 끝점 p, q를 직선으로 잇는 대신, 두 가장자리선의 교점 X를 제어점으로 하는 2차 베지어(연석 반경 곡선)로 잇고, X가 너무 멀면(예리한 각) 제어점을 클램프한다(유도). 접합 폴리곤은 렌더에서만 쓰이고 시뮬 충돌은 커넥터가 계산하므로 해시 불변. 추가로 코너 보도(링 스트립)를 그리면 더 자연스럽다(후속).
- **기존 꺾임 변환 커맨드**: 선택한 차수 2 꺾임 노드 V에 대해 `segment.split`(두 쪽을 T 위치에서 분할) → 중간 조각 제거 → 호 segment 추가를 하나의 `batch`로 만든다. 노드 삭제 커맨드가 없으므로 V 고아 노드 처리는 **미검증**(구현 시 확인).

### A-4. planRoad 확장 스케치 (설명만, 코드 변경 아님)
- 입력: `RoadPlanInput`에 `corner?: { prev: ResolvedPoint(node, 차수1) }` 또는 도구가 직접 3점 `(prevAnchor, V, next)`을 넘겨 `planRoad`가 [직선(anchor→P0) , 호(P0→P2, control=V), (직선 P2→next는 다음 클릭에서)]를 생성.
- 두 가지 상호작용 모델:
  1. **지연 확정**(권장): 도구가 마지막 클릭 점을 보류하고, 다음 클릭에서 코너를 확정해 [이전 직선 + 호]를 커밋. 미리보기에서 사용자는 항상 둥글어진 최종 모양을 본다. 종료는 더블클릭/Enter/툴 전환. (현재 "클릭마다 커밋"과 달라 사용자 습관 변화가 있음)
  2. **소급 편집**: 클릭마다 커밋하되 새 클릭이 꺾임을 만들면 이전 segment 꼬리를 호로 교체하는 batch. 현재 습관 유지, 대신 `segment.split`/`remove` 조합 필요.
- 둘 다 결정론적이며 서버는 평범한 batch를 검증. 필렛 ON/OFF 토글(예: `R` 혹은 툴바 버튼)과 반경 배수 조절 권장.

## B. 도로 그리기 UX

### B-1. 현황과 문제 (확인: 코드)
- 직선 모드는 시작·끝 2클릭이 전부이고 꺾임은 별도 클릭의 연속 그리기. 곡선은 3클릭(제어점이 격자 스냅). 격자 스냅이 기본 8 m라 자유로운 각도가 어렵고, 스냅이 항상 켜져 있어 "딱딱함"을 만든다. 힌트는 길이/방위/교차 수만 표시.

### C-2. 현재 느낌이 거친 이유 (코드에서 추정, 사용자 체감은 재현 필요)
1. 고스트가 `pointermove`마다 위치·각도가 즉시 바뀐다(보간 없음).
2. 길이방향이 8 m 격자로 건너뛴다(`snapAlong`).
3. 최근접 도로가 바뀌는 경계에서 방향(앞면이 향하는 쪽, ±)이 튄다(히스테리시스 없음).
4. 곡선 도로에서 접선은 2 m 폴리라인의 변 방향이라 각도가 계단형으로 변한다(`tangentAtLength`) — 넓은 건물일수록 도로와 앞면이 어긋나 보임.
5. 회전은 15° 단계뿐이고 정렬 상태에서 사용자 회전 의미가 불명확(`placeAt`은 정렬되면 `buildingRotation`을 무시).

## D. 곡면 건물

### D-1. 데이터 모델 비교

| (c) 복셀별 "round" 수정자 | 셀 단위로 모서리 플래그 | 가장 직관적인 편집 | 영역/층 병합 규칙 복잡, 셀 키 구조 확장 | 스튜디오 모델 전반 |
| (d) 원기둥 등 프리미티브 `shape` | `{kind:'cylinder', r}` | AI에 간단 | 충돌 위해 어차피 다각형 변환 필요, 종류가 늘수록 계약 팽창 | 필드 + 분기 |

**권장: (b')를 MVP, 스튜디오에는 VoxelStyle 수준 `round`(스타일 단위로 영역 윤곽에 적용)로 노출.** (c)처럼 셀 단위가 아니라 "같은 스타일 영역"의 윤곽 모서리에 반경을 적용하므로 `voxelsToParts`의 기존 그룹핑을 그대로 쓰고, `styleKey`에 round를 포함시키면 서로 다른 반경은 별개 영역이 된다. (a)는 P5d 이후 "자유 곡선 건물"이 필요해질 때.

### D-2. `partOutline`의 둥근 윤곽 생성 (유도)
- 입력: 직교 윤곽(사각형 포함) + 반경 r. 각 **볼록** 꼭짓점에서 양 변 길이가 r 이상이면 길이 r 만큼 물러난 두 점 사이를 1/4원 호(내부 점 n개)로 대체. 변 길이가 부족하면 r을 `min(r, 최소변/2)`로 제한 → r = w/2 = d/2 이면 원.
- **결정론:** 호의 점은 `Math.sin/cos` 직접 호출 대신 고정 분할수(예: 1/4원당 4~6분할)의 **상수 표**를 코드에 하드코딩한다. V8은 일관되나 다른 엔진은 마지막 비트가 달라질 수 있어, 서버 검증과 클라이언트 미리보기가 경계 사례에서 어긋나는 것을 방지(위험 완화, 필요성은 보수적 판단).
- 정점 수: 직교 L형(6꼭짓점, 볼록 5) × 호 5점 = 약 30점 → `footprintVertices=32` 제한과 충돌 가능. 둥근 윤곽은 **저장값이 아니라 파생값**이므로 이 제한은 직교 원본에만 적용, 파생 정점 수 상한(예: 96)은 별도 상수.
- 검증 규칙: `round`는 0..`min(w,d)/2`(footprint가 있으면 최소 변 길이/2), 지붕은 flat 강제(P5d에서 dome/cone 추가).

### D-3. 파사드(창) 매핑
- 현재 벽 변 하나가 `aWall=(u, v, L)`로 u=변 따라 거리, L=변 길이. 곡면을 N각형 면으로 만들면 **면마다 창 칸 수가 따로 정해져** 칸 폭이 불균일하고 면 경계에서 창이 끊김.
- 해결: 연속된 "부드러운 변"들(이웃 변 사이 꺾임 < 약 25°)을 한 묶음(run)으로 보고 **u를 run 시작부터의 누적 호 길이, L을 run 전체 길이**로 설정(정점 데이터만 바꿈, 셰이더 변경 없음). 셰이더의 `bayW = L / round(L/3.2)` 계산이 run 전체에 균일한 칸 폭을 주고, 모서리 솔리드 처리(`step(0.25,u)*step(u,L-0.25)`)는 run 양 끝에만 걸린다. 원기둥은 시작=끝이 같은 점이라 이음매에 솔리드 기둥 한 줄이 생기는데 건축적으로 어색하지 않음.
- 법선: 부드러운 run 내부는 정점 법선을 이웃 면 법선 평균으로 하여(현재 `GeometryBuilder.tri`는 면 법선 고정) 조명 면 분할(faceting) 방지. 이를 위해 `walls()`가 쿼드의 4개 정점에 각각 법선을 주도록 확장(내부 작업).
- 곡벽 위 소품(발코니, 간판): 현재 `BuildingProp.rot`은 0..3 쿼터턴 → 곡벽에는 방향이 맞지 않음. 곡면 파트에서는 소품 스냅을 평면 변에만 허용하거나 각도 일반화(계약 변경)가 필요 → 후속.
- 지붕 장비(`roofRows` 스캔라인 기반 태양광 등)는 임의 다각형에서도 동작할 것으로 보이나 곡면 테스트 필요(미검증).

### D-4. 지붕
| 지붕 | 방법 | 비고 |
|---|---|---|
| 평지붕 | 기존 `cap()`(ShapeUtils.triangulateShape) | 임의 단순 다각형 OK. MVP |
| dome(돔) | 중심에서 링 3~5개 쌓아 올림, 링 정점은 윤곽을 중심 방향으로 축소(원형/타원형 한정이 자연스러움) | `RoofShape`에 'dome' 추가 필요. 삼각형 ≈ 정점수×링수×2 (24×4×2 = 약 190) |
| cone(원뿔) | 윤곽 정점을 꼭짓점 하나로 연결 | 'cone' 추가. 삼각형 = 정점수 |

`RoofShape`는 `model.ts` 타입 + `validate.ts` 허용 목록 + AI 스키마 + 스튜디오 UI + `roofHeight` 모두 연동 → **계약 변경, 의회 결정 필요**. 박공/피라미드 파트가 이미 있는 사각형에 한해 round를 허용하고 지붕을 강제 flat으로 할지(MVP), 아니면 둥근 윗면에도 pyramid를 cone처럼 해석할지(편법)는 결정 사항.

### D-5. 충돌/겹침/시뮬 영향
- 충돌: `polygonsOverlap`, `intersectionArea`(삼각분할 + 볼록 클립), `polygonsBlockRoad`(점-다각형, segmentDistance)는 임의 단순 다각형을 지원(확인: 코드). 정점이 ~30개면 삼각형 ~28개, 쌍당 최악 ~800회 클립이고 `bounds` 사전 거절이 있어 현실적 부담은 낮음(추정, 벤치 필요).
- 근사 오차: 내접 N각형은 진짜 원보다 약간 안쪽 → 1/4원 6분할 시 최대 반경 오차 `R(1−cos(π/24))≈0.86%`R (유도). 도로 여유 `ROAD_CLEARANCE_EPS=0.05 m`와 비교해 R=6 m에서 0.05 m로 같은 자릿수 → 경계 판정이 아주 약간 느슨해질 수 있음. 외접(바깥 확장) 또는 호 내부점을 원 위에 두되 접선 점을 외접으로 보정하는 방법이 있으나 MVP에선 허용.
- 시뮬: `packages/sim`은 윤곽 함수를 직접 쓰지 않음(확인: grep). `buildingMetrics`(면적)가 `growth/planning`을 통해 수요에 쓰이므로 **둥근 파트의 면적이 약간 작아져** 수요 계산이 미세하게 달라진다 — 기존 건물은 round 필드가 없으므로 불변(골든 해시 불변). 문(door) 위치 계산 방식은 시뮬 외부(shared) 구현을 확인하지 못함 → **미검증**, 구현 시 grep.

### D-6. 스튜디오/AI 적합성
| 항목 | 방안 |
|---|---|
| 스튜디오 | 팔레트에 "모서리 둥글게: 없음/작게(2m)/크게(4m)/원형(최대)" 스타일 옵션. 즉시 보기(셀 큐브)는 그대로, 굽기 후 메시에 둥근 윤곽 표시(기존 "느린 굽기 중 셀 뷰" 메커니즘 활용). 셀은 여전히 직교 → 편집·되돌리기·저장 구조 불변. 열기: `round`를 가진 파트는 직교 원본 윤곽으로 복원 |
| AI | `create_building_design` 블록에 `corner_radius: integer|null`(셀 단위 0~N) 추가. strict 스키마 규칙(null 허용 필드는 required) 준수. 설명에 "원기둥 = w=d, corner_radius = w/2" 예시. 이미지→건물(보고서 11)에서 원형 타워 인식에 바로 활용 |
| 성능(three.js) | 디자인 1개당 1회 굽기 + 인스턴싱이라 정점 수가 도시 규모와 무관하게 디자인 수에만 비례. 원기둥(24각형, 층 수와 무관): 벽 48삼각형 + 지붕 22 ≈ 70삼각형(박스 약 12) — 디자인 수십 개에서도 무시할 수준. `ExtrudeGeometry`는 `curveSegments` 옵션과 `Shape.absarc`를 지원하나(공식 문서 본문은 못 읽음, 일반 지식 — 미검증), 우리는 자체 `GeometryBuilder`에 정점을 직접 넣으므로 불필요 |
| 고스트 | `ghostGeometries`가 `partOutline`을 `THREE.Shape`로 압출하므로 둥근 윤곽도 자동 반영 |

**의회(council) 결정이 필요한 것**
1. 필렛을 **문서에 굽기(A1, 권장)** vs 컴파일 파생(A2): A2는 `compileNetwork`·골든 해시 변경.
2. 필렛 반경 정책(R_min = 폭+여유, 도로 타입별 R_cap) 기본값과 "꺾임 자동 둥글림 기본 ON" 여부.
3. 그리기 종료 방식(지연 확정 vs 소급 편집)과 우클릭 의미.
4. `BuildingPart.round` 추가(계약 변경)와 dome/cone `RoofShape` 확장 시기.
5. 일반 다각형 곡선 건물(a)을 장기 목표로 둘지.
