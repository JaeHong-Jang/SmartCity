# Research: 공공부문 3D 디지털트윈 뷰어 같은 "현대 도시" 외관 — CC0 에셋·절차 생성·원경 산·판교 셔틀·성능 예산
> 결정하려는 것: 도시와 차량을 왕숙 지구 3D 뷰어 수준(가로수 열, 붉은 벽돌 보도, 유리·화이트 포디움 건물, 백색 아파트 단지, 옥상 녹화, 지평선의 산, 현대적 차량)으로 "현대화"할 때 (1) 외부 CC0 에셋을 쓸지 절차 생성으로 갈지, (2) 산 배경을 어떻게 싸게 넣을지, (3) 5,000대·2,000동 규모에서 iGPU 예산을 지킬 수 있는지, (4) 후속 단계의 판교식 자율주행 셔틀+관제를 어떻게 모델링할지
> 작성: sc-researcher (Sonnet 5.5) · 2026-10-31
> 선행 문서: `13-realistic-city-look.md`, ADR 0013(§6 외관·§7 예산), ADR 0010(차량 외관 변주)

## 요약 (5줄 이내)
1. **CC0 3D 에셋은 Kenney(Car Kit·Nature Kit·City Kit 시리즈)와 Quaternius(Stylized Nature MegaKit·Downtown City MegaKit·Cars/Public Transport/Ultimate Nature)가 공식 페이지에서 CC0로 확인된다.** 그러나 전부 **로우폴리 스타일라이즈드**라서 "반사실적 공공부문 뷰어" 룩과는 거리가 있다(특히 차량·건물). 트리 모델은 쓸 만하지만 차·건물은 절차 생성이 목표 룩에 더 맞다.
2. **Poly Pizza는 모델별 라이선스가 섞여 있다(CC0와 CC-BY 혼재, 번들도 혼재).** 사용하려면 모델 단위로 CC0 표기를 확인하고 목록을 남겨야 한다. 사이트 약관은 AI 학습 사용 금지 조항도 있다. 기본 권고는 "Kenney·Quaternius 원본 페이지에서만 받기".
3. **권장 방향은 하이브리드**: 차량·건물·아파트·유리 커튼월·벽돌 보도는 절차 생성(기존 `vehicleModels.ts`의 부품 합성 방식 확장), 가로수는 Quaternius Stylized Nature MegaKit 또는 절차 생성 중 시각 비교 후 결정, 가로등·가구는 절차 생성(수십~수백 삼각형).
4. **원경 산**은 "저폴리 산 링 메시 1개 + 2~3겹 실루엣 + 안개색 블렌딩"이 가장 싸다(드로 콜 +2~3, 삼각형 수천). 지평선 경계 문제(ADR 0013의 "지평선 선" 진단)도 함께 해결한다.
5. **판교 자율주행 셔틀(제로셔틀)**은 11인승(보도마다 9·11·5인승으로 불일치) 무운전석 소형 전기 버스, 시속 25 km, 경기도자율주행센터(차세대융합기술연구원 소속)가 운영, 관제센터가 CCTV 141대·V2X로 연계. 정확한 전장·전폭은 **미검증**(공식 제원을 확인하지 못함). 후속 단계 설계용 요약만 §4에 둔다.

## 0. 현재 코드 상태(확인) — 에셋 도입 판단의 전제
- 차량은 이미 **절차 생성**이다: `apps/web/src/render/vehicleModels.ts`가 `CAR_CLASSES = sedan, suv, hatch, van, pickup, taxi`와 비율(45/25/12/8/6/4 %), 색상 팔레트(흰·검정·은·회·남·빨 등 가중)를 id 해시로 정하고, `vehicles.ts`는 박스 부품을 정점 색으로 합쳐 클래스별 `InstancedMesh`로 그린다(`BoxGeometry` → `mergeGeometries`). 즉 "차를 현대적으로"는 새 GLB 도입이 아니라 **부품 합성 형상을 둥글고 정교하게 개선**하는 쪽이 코드 구조에 맞다.
- 건물 창문·야간 점등은 셰이더/지오메트리 쪽에 이미 있다(ADR 0013 기각표: "창문 셰이더 신규 구현 — 이미 구현됨(buildingGeometry.ts)").
- 가로수·가로등은 아직 없다(`13` 문서 §0, 계획 P6c-2: 단일 InstancedMesh 2~3개, 드로 콜 +4 이내).
- 따라서 이 보고서의 에셋 후보 중 "가져다 쓸 가치"가 큰 것은 **나무(및 일부 가구)** 이고, 차량·건물은 참고 형상 정도다.

## 1. 무료 CC0 3D 에셋 (상용 안전, 오픈소스 웹앱)

### 1.0 라이선스 판단 원칙
- 공식 페이지에 "CC0"가 명시된 것만 "권장 후보"로 올렸다. 라이선스 URL은 대부분 `https://creativecommons.org/publicdomain/zero/1.0/`로 링크되어 있었다(페이지 직접 열람).
- CC0는 저작자 표시 의무가 없다. 다만 레포의 `docs/`(예: `THIRD_PARTY.md`)에 출처·버전·내려받은 날짜를 기록하는 것을 권한다(이 항목은 내 제안이며 라이선스 요건 아님).
- "개인 사용 무료", CC-BY, 출처 불명, 팬메이드(Sketchfab·TurboSquid 등)는 **추천하지 않았다**. 아래 "주의" 열에 표시.

### 1.2 주의/플래그 (라이선스 불명·표시 필요)
- **Poly Pizza**: 번들 단위 표기를 믿지 말고 모델 페이지의 CC0 배지를 확인한다. CC-BY 모델은 표시 의무가 생기므로 채택하지 않는다(요청 규칙).
- **Quaternius**: 일부 팩의 Source/Pro 변형과 Patreon 전용 모델(예: LowPoly Cars의 Cop SUV는 Patreon 전용 — itch.io 설명 검색 요약)이 있다. **무료 Standard 범위의 CC0만** 사용하고 어느 파일을 썼는지 기록한다.
- **Kenney**: "Do not use our logo"만 제한(https://kenney.nl/support 직접 확인). 에셋은 CC0, 이름 표기는 선택.
- 1.1 표에서 "미검증"인 값(삼각형 수, 개별 차종 목록)은 **실제 zip을 내려받아 glTF 뷰어/three.js `renderer.info`로 측정**하기 전에는 의사결정 근거로 쓰지 않는다. 이번 조사에서는 정책상 레포로 내려받지 않았고, kenney.nl 다운로드 직링크도 페이지 소스에서 확인되지 않았다.
- 그 외 후보(Sketchfab, TurboSquid, CGTrader, OpenGameArt 개인 업로드 등)는 이번 조사에서 라이선스를 1차 페이지로 검증하지 못해 **추천하지 않는다**. OpenGameArt는 CC0/CC-BY 등 혼재.

## 2. 절차 생성 대안 (에셋이 맞지 않는 곳)

> 이 절의 수치·패턴은 일반 그래픽스 지식과 현재 코드 구조에서 도출한 **설계 제안**이다. 한국 공공 뷰어의 실제 외관은 요청자가 말한 시각 특징을 기준으로 삼았고, 해당 뷰어를 직접 열람해 검증하지는 못했다(§5 미해결 참고).

### 2.1 가로수·가로등 (인스턴싱, 원거리 빌보드)
- **나무 형상 3단계 LOD (인스턴스 버퍼 분배 방식)**: three.js `InstancedMesh`는 인스턴스 개별 LOD가 없다(공식 문서: `count`·`instanceMatrix`·`computeBoundingSphere()` — https://threejs.org/docs/pages/InstancedMesh.html 직접 확인). 따라서 카메라 거리별로 인스턴스를 서로 다른 메시에 나눠 담는다.
  | LOD | 거리(제안) | 형상 | 삼각형(제안) |
  |---|---|---|---|
  | 0 | < 60 m | 줄기 8각 원기둥 + 수관 이코스피어 2~3덩이(정점 색 잎 변주) | 120~250 |
  | 1 | 60~200 m | 줄기 4각 + 수관 1덩이(저분할) | 30~60 |
  | 2 | 200~600 m | 교차 쿼드 2장 또는 십자 빌보드 1장 | 4~8 |
  | 3 | > 600 m | 컬링(안개에 묻힘) 또는 지면 색 번짐 | 0 |
  전환은 `dirty` 시점이 아니라 **카메라가 일정 거리 이상 움직였을 때만** 인스턴스 재분배(이동 중 매 프레임 재분배 금지 — ADR 0013 "드래그 중 재계산 금지" 원칙).
- **바람 없는 정적 처리**: 정점 애니메이션을 두지 않으면 셰이더가 단순하고 `InstancedMesh` 한 개로 충분. 연출이 필요하면 가장 낮은 LOD에만 정점 셰이더 sway(옵션, 후속).
- **종 다양성**: 인스턴스 색(`setColorAt`) + 크기 ±15 % + Y축 회전 랜덤으로 단일 메시를 3~4 변종으로 보이게 한다. 공공 뷰어 특징인 "열식 가로수"는 규칙 간격(8~10 m)에 노이즈를 거의 넣지 않고, 중앙분리대는 관목 띠(박스 + 색) 한 줄을 추가한다.
- **배치**: 도로 세그먼트 인도 폭 안쪽, 결정적 시드 해시, 횡단보도·교차로 반경·건물 출입구 반경은 제외(ADR 0013 P6c-2 규칙 그대로). 침엽수는 공원·언덕 쪽에 소수.
- **가로등**: 원통 기둥(6각) + 곡선 암 + 조명 박스 ≈ 40~80 삼각형. 야간은 헤드(조명 박스)만 이미시브 색, 실제 포인트 라이트는 쓰지 않는다(iGPU). 간격 25~35 m(제안, 미검증).
- **그림자**: 소형 요소는 `castShadow=false`, 나무만 그림자 옵션 처리(13 문서 Q6과 일치).

### 2.2 현대 차량 (둥근 차체 + 유리 캐빈 + 바퀴 + 램프)
- 현재: 박스 부품 합성(`BoxGeometry` → 병합, 정점 색)이라 각진 인상이 크다.
- 제안: 차체를 **슈퍼엘립스/둥근 박스(모서리 챔퍼가 있는 `ExtrudeGeometry` 또는 수작업 정점)** 로 만든다.
  - 구성: 하부 차체(둥근 모서리) + 캐빈(앞뒤 경사 윈도우, 짙은 유리색 정점) + 휠 4개(8각 원기둥) + 헤드램프/테일램프(작은 박스, 이미시브 후보) + 거울·번호판 표현은 선택.
  - 클래스(sedan/suv/hatch/van/pickup/taxi)는 기존 `CAR_CLASSES`와 동일하게 유지하고 `carBodyParts`/`carFixedParts` 부품 정의만 교체하는 방식이 코드 변경을 최소화한다.
  - 삼각형 예산: **LOD0 근거리 250~400 삼각형 / LOD1 중거리 60~100 / LOD2 원거리 박스 12**(제안). 5,000대 전체를 LOD0로 그리면 약 125만~200만 삼각형으로 iGPU 예산을 위협하므로 §5의 거리별 분배가 필수.
  - 신호·미래 요소: 자율주행 셔틀(§4)과 구급·경찰·소방은 **같은 파이프라인의 새 클래스**로 추가(색·라이트바·루프 센서 돔 부품).
- 환경 반사: 차체 `MeshStandardMaterial`의 `envMap`을 하늘 PMREM과 공유하고 `metalness 0.1~0.3`, `roughness 0.35~0.5`를 주면 유리·도장 하이라이트가 생긴다(§2.4).

### 2.3 한국형 아파트·오피스 파사드
이 절은 요청자가 제시한 시각 특징을 재현하기 위한 **패턴 목록**이다.
- **아파트 단지 패턴 요소**
  | 요소 | 구현 방식 | 비용 |
  |---|---|---|
  | 발코니 띠(수평) | 외벽 셰이더에서 층 단위로 약간 어둡거나 밝은 수평 띠, 또는 지오메트리 돌출 박스(층마다) | 셰이더면 0 |
  | 측벽 세로 색 띠 | 외벽 `onBeforeCompile`에서 월드 X 또는 건물 로컬 좌표 기준 세로 줄무늬(예: 아이보리 바탕 + 파스텔 청·적색 한 줄), 건물마다 `instanceColor` 또는 속성 값으로 색상 선택 | 0 |
  | 계단실 코어 | 건물 입면 중앙/끝의 세로 띠(어두운 창 한 줄) | 셰이더 |
  | 옥탑(crown) | 최상층 위 2~3층 분량의 후퇴한 박스 + 단지명 띠(브랜드 이름 대신 **임의 문자 없는 색 띠**; 실제 브랜드 사용은 피한다) + 물탱크/설비 박스 | 건물당 박스 2~4개 |
  | 단지 구성 | 같은 형태의 동을 평행 배열·층수 변주(15~25층), 흰색 중심, 판상형/타워형 혼합 | 인스턴싱 가능 |
  | 옥상 녹화 | 평지붕 상단에 녹색 패치(옥상정원 박스), 일부는 태양광 패널 | 박스 1개 |
  층고 3 m 기준(13 문서 근거표)을 유지한다.
- **유리·화이트 포디움 오피스**: 저층 2~4층 포디움(넓은 돌출, 연회색 패널 + 대형 유리) + 상부 타워(좁음, 유리 커튼월). 1층 주출입 캐노피 박스. 상층 후퇴(setback)로 실루엣 변화.
- **적용 위치**: 건물 사용 용도(`zoning`/건물 종류)가 이미 있는 경우 용도에 따라 외벽 셰이더 변종을 고르는 것이 자연스럽다. 용도 분류 코드는 이번에 읽지 않았다(미확인 — 구현 전 `buildingGeometry.ts`·`buildingTone.ts` 확인 필요).

### 2.4 유리 커튼월 + 하늘 환경 반사
- **PMREM**: `THREE.PMREMGenerator.fromScene(scene, sigma, near, far)`로 하늘 장면을 환경맵으로 만들고 `scene.environment`에 연결한다. `Sky` 메시 반경이 크므로 `far`를 그보다 크게 줘야 한다(공식 문서의 `Sky` 예: scale 450000, far 1000000 — https://threejs.org/docs/pages/PMREMGenerator.html 직접 확인). 낮/밤 전환 시 **환경맵 재생성 빈도를 제한**(예: 태양 고도가 일정 각 이상 변할 때만; 제안)하여 iGPU 비용을 막는다. 현재 하늘이 `scene.background` 그라디언트이므로(`sky.ts`) 이 방식과의 통합은 구현 단계에서 설계해야 한다.
- **재질**: 유리 면은 `MeshStandardMaterial` `metalness 0.8~1.0`, `roughness 0.05~0.2`, 색 어두운 청회색 + `envMapIntensity` 조절. 투명도(`transparent`)는 정렬·오버드로우 문제로 **쓰지 않는다**(불투명 반사 유리).
- **멀리온(mullion)**: 외벽 셰이더에서 UV/월드좌표 기반 얇은 격자선(어두운 알루미늄색)을 그린다. 창문 점등은 기존 `occ`와 연결(13 문서 M2).
- **비용 주의**: 큰 면적에 PBR 반사를 모두 쓰면 프래그먼트 비용이 증가한다. 근거리 건물만 고품질 재질(유리 반사 강하게), 원거리는 단순 `MeshLambertMaterial`급으로 낮추는 품질 슬라이더 제안.

### 2.5 붉은 벽돌 보도
- 현재 `paving.ts`/`roads.ts`에 보도 렌더가 있다(세부 내용 미열람).
- 제안: 보도 재질에 벽돌 패턴을 **프래그먼트 셰이더**로 그린다(월드 좌표 기준 0.2×0.1 m 격자 + 오프셋 줄눈, 색은 벽돌 3~4색 노이즈 변주). 텍스처 파일 없이 해상도 무관, 에셋 라이선스 문제 없음. 멀리에서는 평균색으로 감쇠(미스매치 앨리어싱 방지: `fwidth` 기반 필터). 이 방식은 `ground.ts`의 8 m/64 m 격자 셰이더와 같은 접근이다.

## 3. 원경 지형(산) — 저비용 지평선

### 3.1 선택지 비교
| 선택지 | 장점 | 단점 | 사례/근거 |
|---|---|---|---|
| **A. 저폴리 산 링 메시** (도시 중심 반경 R≈5~8 km, 노이즈 높이 200~800 m, 링 폭 1~2 km) | 드로 콜 1, 삼각형 수천(링 세그먼트 256×8 ≈ 4k), 모든 방향 커버, 플랫 셰이딩+정점 색 | 반복 느낌(시드 변주·스케일 다양화 필요), 도시와 겹치지 않게 반경 설정 | three.js 포럼에 절차 로우폴리 지형(플랫 셰이딩+정점 색) 사례: https://discourse.threejs.org/t/how-can-i-make-this-world-more-fancy/32275 (검색 요약) |
| **B. 레이어 실루엣 + 안개** (2~3겹 링, 멀수록 연하고 안개색에 가까움) | 대기 원근이 확실해서 "멀리 있는 산" 느낌, 지평선 선 제거 | 레이어마다 드로 콜+1 (총 +3), 야간에 안개색 갱신 필요 | 일반 원리. 안개는 three.js `Fog`(선형)/`FogExp2`로 구현 가능(공식 `Fog`/`FogExp2` 존재는 13 문서가 확인). 안개색이 하늘색과 일치해야 함(`dayNight.ts`가 이미 갱신) |
| **C. 헤이트맵 원경 지형** | 현실적 능선, 지면 색과 이음새 처리 가능 | 지형 고도와 도로·건물 고도 모델 충돌(ADR 0003) — 13 문서에서 L3(대형, 고위험)로 분류 | GitHub 예: 정점 셰이더에서 FBM 노이즈로 산 생성 https://github.com/RobertoLovece/Mountain (검색 요약; 폴리 수가 많아 저사양 경고) |
| **D. 스카이박스/파노라마 이미지(산 실루엣 포함)** | 구현이 가장 쉬움(드로 콜 1) | 이미지 에셋 라이선스 필요, 카메라 이동 시 시차 없음, 저고도 시점에서 해상도 문제 | three.js `GroundedSkybox`(지면 투영 스카이박스) 공식 애드온: https://threejs.org/docs/pages/GroundedSkybox.html (검색 요약) |

### 3.2 권장
- **A+B**: 링 2~3겹(반경 6/8/10 km, 높이 300/500/700 m 등 제안값). 각 링은 `MeshBasicMaterial`/`fog: true`의 단색+정점 색, `depthWrite` 적절히 처리. 안개 far(현재 5200 m → 13 문서 Q1에서 3500 m 정도로 조정 제안)를 링의 바깥 반경보다 작게 두면 링이 안개색으로 완전히 묻혀 사라진다. 그래서 **링은 안개 far의 약 70~90% 지점 이내**에 두고 안개 일부 투과를 허용하거나 링 재질 `fog: false` + 직접 안개색 혼합 중 선택해야 한다(구현 시 시각 확인으로 결정, **미검증 설계 포인트**).
- 지면 12 km 평면의 가장자리를 링이 가리게 하여 "지평선 선" 문제(13 문서 진단)를 같이 해소한다.
- 한국 도시 정서를 위해 산 색은 짙은 녹청~회청, 능선은 부드러운 곡선(플랫 셰이딩 대신 스무스 셰이딩 + 정점 색 그라디언트 권장; 시각 비교 후 결정).
- 이 변경은 13 문서의 L1(원경 스카이라인 임포스터)·ADR 0013 P6c-3과 같은 "원경 레이어" 작업이므로 한 번에 설계하는 것이 좋다.

### 3.3 인용 가능한 외부 사례(제한적)
- 공식 사례로 확인한 것은 three.js `GroundedSkybox` 애드온과 위 포럼/GitHub 2건뿐이다(모두 검색 요약 수준, 직접 열람 못함). **웹 도시 뷰어가 지평선 산을 어떤 방식으로 넣는지에 대한 1차 자료는 확보하지 못했다**(미검증). Cesium/Google 3D Tiles처럼 실제 지형을 올리는 방식은 이 프로젝트의 가상 도시와 맞지 않고(13 문서: Google 타일 정책상 부적합), 요청자가 본 "왕숙 3D 뷰어"는 지형 위에 실제 지구 데이터를 얹은 것으로 추정하나 직접 확인하지 못했다.

### 4.3 "온보드 자율주행 + 중앙 관제/에이전트" 구조 (한국 스마트시티 실증 맥락)
- **판교 제로시티 관제**: 바이라인네트워크 기사(직접 확인)에 따르면 자율주행통합관제센터가 제로시티의 **고화질 CCTV 141대와 IoT 센서 데이터**를 통합 플랫폼에서 모니터링·분석하고, 돌발상황을 "이벤트"로 분류해 필요한 차량에만 정보를 LTE로 전달한다(기존 WAVE 방식은 근처 차량에 무작위 방송). 이는 우리 프로젝트의 "센서 = 눈, 관제 = 인지" 구조(ADR 0013 센서·감지)와 개념이 같다.
- **C-ITS**: 국토교통부·과기정통부 보도자료 요약에 따르면 C-ITS는 차량-차량, 차량-도로 통신으로 차량 센서 범위(150~200 m)보다 먼 거리의 교통위험정보를 미리 공유하는 지원 인프라이며, LTE-V2X 조기 실증(~2022)·고속도로 병행 시범(~2023)을 거쳐 2024년 이후 단일 표준으로 전국 확산 계획이었다 — https://smartcity.go.kr/2021/08/26/국토교통부-과학기술정보통신부-맞손-차세대지능/ (검색 요약; 본문 미열람, 계획이 현재 이행되었는지 **미검증**).
- **시사점(후속 설계)**: (1) 차량 의사결정(차선 유지·정지)은 온보드, 관제는 이벤트 방송·허가·원격 모니터링으로 분리, (2) 관제는 센서(CCTV) 데이터로 낙하물 같은 이벤트를 판정해 해당 구간 차량에만 전달(KT 시연 사례, 검색 요약), (3) 우리 시뮬레이터에서는 "자율주행 셔틀 클래스" + "관제 이벤트 전달 지연"을 기존 감지·인지 파이프라인(`policy.detection`)에 얹는 것이 자연스럽다.
- 이 범위는 **현재 외관 작업의 일부가 아니라 후속 Phase**이며, 정확한 법·표준 정의가 필요하면 국토교통부 원문을 확인해야 한다.

### 4.4 시뮬레이션 모델링 시사 (제안)
- 클래스 `shuttle`: 길이 5~6 m·폭 2 m·높이 2.4 m 정도의 직육면체형 미니버스 + 루프 센서 돔 + 네 모서리 라이다 박스 + 측면 대형 유리(제안 치수 — 공식 제원 미확인 상태에서의 설정값). 흰색 바탕 + 포인트 색 띠(상업 로고 사용 금지).
- 거동: 낮은 속도(≤25~30 km/h), 정류장 정차, 호출형 모드(2022년 이후) 여부는 기능 선택지.

## 5. 성능 — 우리 규모의 삼각형·드로 콜 예산 (노트북 iGPU)

> 모든 숫자는 **제안 시작값**이며 실측으로 확인해야 한다(13 문서 §3.1과 동일 원칙). 기존 기준: 건물 2,000, 차량 5,000, 데스크톱 60fps, 메인 드로 콜 < 150, 13 문서 iGPU 제안 삼각형 ≤ 1.5~2 M(화면에 보이는 것).

### 5.1 요소별 예산표
| 요소 | 수량(최대, 가정) | 삼각형/개 | 합계 삼각형 | 드로 콜 | 비고 |
|---|---|---|---|---|---|
| 가로수 LOD0 (<60 m) | 화면 내 ~300 | 200 | 60k | 1 | 인스턴스 버퍼 분배 |
| 가로수 LOD1 (60~200 m) | ~1,500 | 45 | 68k | 1 | |
| 가로수 LOD2 (200~600 m) | ~3,000 | 6 | 18k | 1 | 교차 쿼드, 알파 테스트 시 오버드로우 주의 |
| 가로등 (전체) | ~2,000 | 60 | 120k | 1 | 원거리는 컬링(셰이더 거리 페이드) |
| 차량 LOD0 (<100 m) | ~300 | 300 | 90k | 클래스 6종 × (본체+고정부) ≈ 12 | 현재 구조 유지 |
| 차량 LOD1 (100~300 m) | ~1,500 | 80 | 120k | +6~12 | |
| 차량 LOD2 (>300 m) | ~3,200 | 12 | 38k | +6 | 단색 박스 |
| 건물 2,000동 | 2,000 | 가변(창 셰이더 사용) | 현행 유지(미측정) | 현행 | 건물 청크화는 13 문서 M4 |
| 산 링 2~3겹 | — | — | ~10k | 3 | 안개 처리 |
| 아파트 옥탑·발코니 돌출 추가 | 필요한 건물만 | 20~80 | ≤ 100k | 인스턴싱 시 +2~4 | 셰이더 우선 |
| **추가분 합계(식물·가구·차량·산)** | | | **≈ 0.5 M 전후** | **약 +30~45** | 현재 baseline 위에 추가되는 증분 |

- 계산 근거: 위 표의 곱셈 합. 차량 5,000대 전체를 LOD0 300 삼각형으로 그리면 1.5 M으로 예산을 단독 소진하므로 거리별 분배가 필수다. 실제 화면에 동시에 보이는 수는 프러스텀 컬링 전에는 과대평가일 수 있다.
- 드로 콜은 **재질 수**가 지배한다: 모든 정점 색 단일 머티리얼 + 클래스별 `InstancedMesh`로 합치면 위 증분이 현재 150 미만 목표를 크게 깨지 않는다. 증분 +30~45는 최악의 상한(모든 LOD·클래스가 동시에 인스턴스 보유)이며 비어 있는 메시는 `count=0`이면 그려지지 않는다고 가정(three.js `InstancedMesh.count` 문서; 비활성 메시는 `visible=false`도 가능).

### 5.2 LOD·임포스터 전략
1. **버퍼 분배 LOD(권장)**: `InstancedMesh` 여러 개(LOD별)에 인스턴스를 나눔. 카메라가 일정 거리/시간 이상 움직일 때만 재분배. 차량은 매 프레임 위치가 변하므로 LOD 판정 비용(5,000대 거리 계산)이 JS 병목이 되지 않도록 **프레임당 일부만 갱신**(라운드로빈)하거나 거리 밴드 해상도를 2~3개로 제한.
2. **BatchedMesh**: 서로 다른 지오메트리(나무 변종, 차종)를 1드로 콜로 묶는 후보. `perObjectFrustumCulled`·`setVisibleAt`가 있고 LOD API는 없다(13 문서 §3.2에서 공식 문서 확인 인용). 도입은 측정 후.
3. **임포스터/빌보드**: 원거리 나무와 먼 건물 실루엣에 사용(§2.1, 13 문서 L1). 일반 기법이지만 우리 스택에서의 구체 이득은 **미측정**.
4. **셰이더 거리 페이드**: 가로등·작은 소품은 일정 거리에서 크기 0으로 줄여 컬링(P6c-2에 이미 기록).
5. **그림자**: 차량·가로등·소형 소품 `castShadow=false`. 나무는 근거리만. 그림자 패스가 CS2 사례에서 드로 콜 72%였다는 13 문서 근거를 재사용.
6. **품질 슬라이더**: 반사 유리(PMREM), 나무 LOD0 거리, 후처리 on/off를 묶은 "품질" 옵션. iGPU 기본값은 낮음.

### 5.3 측정 방법(13 문서 §3.3 그대로 + 항목 추가)
- 고정 카메라 3종(탑다운 원거리, 중간, 눈높이)에서 `renderer.info.render.calls/triangles`, 프레임 타임 p50/p95/p99, 그림자 패스 포함 여부를 도입 전·후 기록.
- iGPU 노트북 한 대를 기준기로 고정. 이 조사에서는 **실측을 하지 않았다**.

## 권장안 (MVP / 후속)
**MVP (P6c-2 확장, 코드 변경은 이번 범위 아님)**
1. 가로수 3 LOD + 가로등을 절차 생성 `InstancedMesh`로(§2.1). 나무 비교용으로 Quaternius Stylized Nature MegaKit glTF 1~2종을 같은 LOD0 슬롯에 임시로 넣어 룩 비교(레포에는 승인된 파일만 커밋, 출처 기록).
2. 붉은 벽돌 보도 셰이더(§2.5), 중앙분리대 관목 띠.
3. 차량 부품 합성 형상 개선(§2.2): 둥근 차체·유리 캐빈·램프, LOD 3단. 구급차·경찰·소방은 색·라이트바 부품.
4. 원경 산 링 2~3겹 + 안개/지평선 정리(§3.2) — 13 문서 Q1(안개)과 같은 PR 권장.
5. 측정: §5.3, 도입 전·후 iGPU 기준 기록.

**후속**
- 아파트 파사드 패턴(옥탑, 측벽 줄무늬, 옥상 녹화), 유리 커튼월 + PMREM 반사, 품질 슬라이더.
- 판교형 자율주행 셔틀 클래스 + 관제 이벤트 전달(§4), 헤이트맵 원경 지형(고위험, L3).

## 위험과 미해결 질문
1. **Kenney Car Kit의 실제 차종 목록·삼각형 수**와 Quaternius Stylized Nature MegaKit 나무 삼각형 수는 이번에 측정하지 못했다. 팀이 zip을 내려받아(레포 밖 작업 디렉터리) glTF 뷰어로 측정하기 전에 도입 결정을 확정하지 않는다.
2. **라이선스 기록**: CC0라도 어떤 파일을 어느 날짜에 어디서 받았는지 `THIRD_PARTY` 성격의 문서에 남겨야 한다. Poly Pizza 모델은 모델 단위 확인이 필수.
3. **목표 룩의 1차 자료 부재**: 왕숙 3D 뷰어를 직접 열람하지 못했다(검색 결과는 2022년 LH 시범 서비스 기사뿐). 따라서 "벽돌 보도, 유리 포디움, 흰 아파트" 등은 요청자 설명을 기준으로 한 일반 설계다. 팀이 스크린샷을 레퍼런스 보드로 확보해 두는 것을 권한다(캡처한 이미지는 저작권상 레포 반입 금지, 사내 참고용).
4. **제로셔틀 제원(전장·전폭)과 2023년 이후 운행 상태**는 미확인. 기사 간 인승(9/11/5)·운행 시작(2017/2018) 표기가 충돌한다. 후속 Phase 전에 경기도자율주행센터 공식 자료로 확정.
5. **PMREM 환경 재생성 비용**과 산 링의 안개 상호작용은 이론 설계일 뿐 iGPU에서 측정되지 않았다.
6. 아파트·오피스 파사드 셰이더는 곡면 건물(Phase 5d) UV와의 호환 확인이 필요하다(13 문서 M2 위험 항목과 동일).
7. 이 문서는 코드를 수정하지 않았고 에셋을 레포에 내려받지 않았다.
